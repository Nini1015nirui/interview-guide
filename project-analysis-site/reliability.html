    项目解析 · 可靠性

    异步、一致性与限流：把慢且不可靠的调用管住

    一次大模型调用动辄十几秒，还会失败、超时；进程会重启；用户会刷新、会重复点击。这个项目用一套 Redis Stream 异步模板、几个带围栏的状态机、分层的幂等手段和一段 Lua 脚本，把这些不确定性收拢起来。这一页是面试里“深挖项目”环节最容易被追问的部分。

    要应对的失败模式

    会发生什么项目里的应对细节
    模型调用太慢，HTTP 请求超时异步化请求线程只落库和投递，结果通过状态字段轮询
    消费者处理到一半进程崩溃pending 回收消息未 ACK 会留在 pending 列表，空闲超过 5 分钟被重新认领
    投递到 Redis 失败失败即落状态 + 定时恢复生产者在独立事务里把状态改成 FAILED；题库和语音评估还有调度器重投
    同一消息被处理两次跳过已完成 + 原子领取消费前检查实体状态；题库生成用行锁比较后更新
    旧任务的结果覆盖新任务taskId 围栏每次提交生成新 taskId，写结果前在锁内核对
    刷新页面重复出题幂等键URL 带请求 ID，后端锁 + 结果映射 + 唯一索引
    接口被刷多维限流全局 / IP / 用户多条规则一次 Lua 原子判定
    长事务里调外部服务事务边界规则大模型、S3、HTTP 调用一律放在事务外
    重建数据时失败，旧数据已被删影子写入再提升向量化先写临时数据，成功后同一事务内替换

    Redis Stream 异步模板

    五条异步管线（简历分析、知识库向量化、文字面试评估、语音面试评估、知识库题库生成）共用两个模板基类。子类只需要实现十来个小方法：Stream 名称、消费者组、如何解析消息、如何标记处理中 / 完成 / 失败、如何重试。

    生产者

    AbstractStreamProducer.sendTask 做三件事：构造消息（字段全是字符串，重试次数从 0 开始）、以近似裁剪的方式写入（相当于 XADD key MAXLEN ~ 1000，防止 Stream 无限增长）、失败时回调子类的 onSendFailed。子类在回调里把实体状态改成 FAILED，简历分析和面试评估的回调用的是 REQUIRES_NEW 独立事务，保证即使调用方的事务回滚，失败状态也能落下来。

    消费者

    • 线程模型：每个消费者在 @PostConstruct 时创建一个显式配置的 ThreadPoolExecutor（核心与最大都是 1，守护线程，拒绝策略 Abort），里面跑一个 while (running) 循环；@PreDestroy 时置标志位并关闭线程池。项目规则禁止用 Executors.newFixedThreadPool 这类工厂方法，所以线程池都是手写参数。
    • 消费者组：启动时创建（带 MKSTREAM，已存在返回的 BUSYGROUP 忽略）；消费者名是前缀加 8 位 UUID，每个实例、每次启动都不同，多实例部署时天然分摊消息。
    • 先回收，再读新：每一轮先用 XAUTOCLAIM 认领空闲超过 5 分钟的 pending 消息（每轮最多 10 条，扫描游标按“Stream + 组”记在内存里，下一轮接着扫）；有就先处理这些，没有再用 XREADGROUP 阻塞 1 秒读最多 10 条新消息。回收时如果发现消息已被 MAXLEN 裁剪掉，会打告警日志。
    • 毒消息：解析失败或字段缺失的消息直接 ACK 丢弃并打日志，避免反复失败卡住整个组。
    • Redisson 4.0 兼容：没有消息时 readGroup 和 autoClaim 会因为内部返回空 List 而抛 ClassCastException，RedisService 把它当成“本轮无消息”处理，并在类注释里写明升级后可以删掉。

    管线Stream / 消费者组消息内容状态字段额外的恢复手段

    这套模板的边界

    每条管线每个实例只有一个消费线程，大模型一次调用 20 秒，排队 10 个任务就要等三分多钟；可以改成可配置的并发消费加信号量背压。除题库生成外，其他管线的“领取”只是直接改状态，不是比较后更新，如果某个任务执行超过 5 分钟，可能被别的实例重复认领。失败只落在状态字段，没有死信队列可供人工回放。简历和知识库正文被整篇放进消息体，大文档会占用 Redis 内存，更好的做法是只传 ID，由消费者从对象存储重新读取。

    先提交，再投递

    异步任务最隐蔽的一类 bug 是“消息比数据先到”：如果在数据库事务提交前就把消息发出去，消费者可能读到旧状态，甚至读不到这一行；如果先发消息、后面事务回滚，就产生了“幽灵任务”。项目里有三种写法保证顺序：

    • 事务同步回调：语音面试结束会话时，sendEvaluateTaskAfterCommit 判断当前是否在事务中，是就注册一个 afterCommit 回调，事务提交后才投递。
    • 小事务执行器：简历“重新分析”先用 TransactionalExecutor.run 把状态改回 PENDING 并提交，再在事务外投递。这个执行器还解决了同类方法内部调用导致 @Transactional 失效的问题。
    • 状态服务单独成事务：题库生成先调用 QuestionGenerationStateService.createTask（自带事务）落好 QUEUED 和新 taskId，返回后才发消息；发送失败就把任务标记为 FAILED。

    剩下的缝隙是“提交成功、但投递失败且没来得及改状态”（比如进程恰好在两步之间崩溃），状态会停在 PENDING 或 QUEUED。题库生成和语音评估靠调度器兜底，其他管线靠用户手动重试。完整的解决方案是事务性发件箱（Outbox）：把消息和业务数据写进同一个事务的发件表，再由独立线程扫描投递。面试被问到时可以把这条改进路线讲出来。

    题库生成状态机

    这是整个项目里一致性设计最严密的部分，源于一次真实问题：同一个知识库可以反复点“生成题目”，上一次的 Worker 可能还在跑，它的结果不能覆盖新任务；消费失败后状态也不能一直停在 PROCESSING。提交 7915d65 先写了两个失败的测试复现这两个问题，7cf90b3 定义了状态事务的契约，3ac6178 和 4f5765f 让它们通过。

    几个关键机制

    • 围栏令牌：每次提交生成一个 UUID 作为 taskId，存到知识库行上，消息里也带着它。所有迁移方法都要求“传入的 taskId 等于当前 taskId，且状态等于预期状态”，否则返回 false 什么都不做。
    • 行锁：比较和更新发生在 SELECT … FOR UPDATE（JPA 的 PESSIMISTIC_WRITE）之内，把同一知识库的状态迁移串行化，避免两个消费者同时通过检查。
    • 提交时的校验：知识库必须已经完成向量化；已有 QUEUED 或 PROCESSING 的任务时拒绝重复提交。
    • 参数快照：难度、题量、追问数、方向上限、Provider 序列化成 JSON 存在 question_gen_config，不包含 Prompt、上下文或密钥。重试和恢复时从这里读参数，不依赖消息体。
    • 大模型调用在事务外：检索上下文、调用模型、构建实体都不持有锁；最后一步才开一个小事务，再次核对 taskId 和 PROCESSING 状态，然后删除旧题、保存新题、写入完成状态和“已生成 X 道，跳过 Y 道重复题”的消息。任何一步失败整体回滚。
    • 失败信息脱敏：对外只写“题目生成失败，请稍后重试”，具体异常留在日志里。
    • 前端配合：提交后立即跳到题库页，按 3 秒间隔轮询状态；只有“同一个任务从活动态变成 COMPLETED”时才刷新列表。这条规则来自浏览器实测时发现的问题：页面首次加载读到历史的 COMPLETED 状态，会误把筛选条件切到“草稿”，出现“暂无题目”的假象（20ca85c、1f82388）。
    面试这样说

    异步任务最怕的不是失败，而是“过期的成功”：用户已经重新提交了，老任务才跑完并把结果写进去。我们给每次提交发一个 taskId 当围栏令牌，所有状态迁移都在行锁里比较 taskId 和当前状态，比较失败就丢弃。大模型调用放在锁和事务之外，只有最后的“替换题目 + 标记完成”是一个短事务。

    幂等设计

    刷新不重复出题

    文字面试创建一次要调用两次大模型，耗时十几秒到一分钟。用户在等待时刷新页面，早期版本会再出一套题（0f66810 修复，2ab89e1 又补上了 Redis 映射丢失时的数据库兜底）。

    几个细节：请求 ID 由前端在进入 /interview 时用 crypto.randomUUID() 生成并写进 URL，面试配置放在 history state 里，刷新后都还在；后端要求请求 ID 匹配 [A-Za-z0-9_-]{8,64}，否则拒绝；锁的等待时间 185 秒略长于一次出题的最长耗时，第二个请求会等第一个完成后直接读到结果；代码注释里写着“幂等请求必须先成功落库，再写入易失缓存”，数据库是真相，Redis 只是加速层。

    其他幂等点

    • 上传去重：简历和知识库都按文件内容的 SHA-256（不是文件名）去重，唯一索引兜底，命中直接返回已有记录。
    • 答案写入：(session_id, question_index) 唯一，保存时先查再更新，同一题提交多次只会改同一行。
    • 消费端：所有消费者在处理前检查实体是否已删除、是否已完成；题库生成额外做原子领取。
    • 显式重试：语音评估的 POST 接口语义是“重新生成”：已完成直接返回结果，处理中返回当前状态，PENDING 或 FAILED 会真实重新投递（dab8b57 修复了早期对卡住的 PENDING 只返回原状态的问题）。
    • 前端防重入：React StrictMode 在开发环境会把 effect 执行两次，导致面试会话被创建两次，5c878a3 用 useRef 标记防止重入。

    缓存设计

    文字面试的会话状态（题目列表、当前题号、状态、简历文本）放在 Redis：键 interview:session:{id}，24 小时过期，每次访问续期；另有 interview:resume:{resumeId} 记录某份简历的未完成会话，用于“继续面试”。

    • 读：先查 Redis；未命中就从数据库恢复，题目来自 questions_json，已作答的内容从答案表回填到对应题目，恢复后写回 Redis。
    • 写：提交答案时先写数据库（答案、当前题号、状态，失败直接报错给用户），再更新 Redis；Redis 更新失败不影响正确性，下一次读会从数据库恢复。
    • 语音会话：实体缓存在 voice:interview:session:{id}，1 小时过期；结束、暂停、评估状态变化时直接删除缓存（dab8b57 修复过“评估状态已更新但缓存还是旧的”问题）。

    值得讨论的一点：语音会话缓存的是 JPA 实体本身，实体结构一改，缓存里的旧对象就可能反序列化失败；把缓存对象和持久化实体分开是更稳妥的做法。

    多维限流

    用法

    @RateLimit 是可重复注解，一个方法上可以叠加多条规则，每条规则是一个维度（全局、IP、用户）和一个“每 interval 时间内最多 count 次”的配额，默认单位是秒。所有规则都通过才放行，否则调用同类里的降级方法，或抛出限流异常（错误码 8001）。

    接口规则
    简历上传、创建文字面试全局每秒 5 次 + 单 IP 每秒 5 次
    简历重新分析、知识库重新向量化、题库生成全局 2 次 + 单 IP 2 次（每秒）
    知识库上传全局 3 次 + 单 IP 3 次
    知识库问答：普通 / 流式全局与单 IP 各 10 次 / 各 5 次
    提交答案全局 10 次
    JD 解析单 IP 5 次
    Provider 管理读 30 次、写 5 次、连通性测试 10 次（全局）

    没有加限流的调用模型接口也值得指出：问答助手的会话流式接口、日程解析、语音会话创建和语音评估重试。

    Lua 脚本怎么算

    每条规则对应两个 Redis 键：…:value 存当前剩余令牌数，…:permits 是一个有序集合，记录每次发放（分数是时间戳，成员是“请求 ID:规则序号:数量”）。判断时，可用令牌 = 当前值（不存在则为上限）+ 已经滑出时间窗口的发放记录之和，封顶为上限。这是“滑动窗口 + 过期令牌回补”的组合，精度比固定窗口高，代价是每次放行都要在有序集合里记一条。

    键名形如 ratelimit:{Class:method}:ip:1.2.3.4。花括号是 Redis Cluster 的 hash tag，保证同一个方法的所有维度落在同一个槽位上，这是能在一个 Lua 脚本里同时操作多个键的前提。

    多维原子性：一次真实修复

    一次请求要同时满足“全局”和“IP”两条规则。如果逐条“检查并扣减”，第一条扣了、第二条拒绝，第一条的配额就白白损失了。项目的脚本分两个阶段，ca2e812（合并自贡献者的 PR #39）又修正了其中一个细节：

    修复前

    1. 规则一：删除窗口外的发放记录（已经在写 Redis），计算余量，够。
    2. 规则二：计算余量，不够，返回拒绝。
    3. 请求被拒，但规则一的有序集合已被改写。

    修复后

    1. 阶段一只读：逐条算出可用令牌，任何一条不够立即返回 -i（第 i 条规则失败），一个键都不写。
    2. 阶段二：全部通过后，逐条删除过期记录、写入本次发放、扣减余量，两个键的过期时间设为窗口的两倍。
    3. 拒绝的请求对任何维度都没有副作用。

    这个修复配了 Testcontainers 的集成测试，用真实的 Redis 7 容器验证“多维回滚”和“各维度独立计数”。其他细节：脚本启动时 SCRIPT LOAD 后用 EVALSHA 调用，Redis 重启导致脚本缓存丢失（NOSCRIPT）时自动重新加载再试；返回的负数下标用来定位是哪条规则拒绝的；IP 依次取 X-Forwarded-For 第一段、X-Real-IP 等头，最后才用连接地址。

    安全上的保留意见

    IP 维度直接信任请求头，没有校验可信代理，客户端伪造 X-Forwarded-For 就能绕过单 IP 限制；用户维度读 X-User-Id 头，在没有鉴权的前提下同样可伪造。生产环境应只信任网关写入的头，用户 ID 从认证上下文里取。

    事务边界

    规则只有两句：事务只放在 Service 的公开方法上并保持最小；事务内不调用大模型、对象存储和外部 HTTP。提交 5c878a3 里有一条记录就是修这个问题：原来在 @Transactional 方法里调用大模型，改成只把数据库写入单独放进事务。几个典型场景：

    • 删除知识库：事务内删数据库记录（先把它从所有问答会话的多对多关联里移除，否则外键会阻止删除）；事务提交后删向量数据（失败只记日志）；最后删对象存储文件（失败时日志里带上 storageKey，便于补偿）。顺序是“先删权威数据，再清理衍生数据”。
    • 向量化：几十上百次 Embedding 调用在事务外完成，只有最后“删旧向量 + 提升新向量”两条 SQL 放在一个事务里，见 业务模块。
    • 题库生成：见上文状态机。

    源码里也能找到几处没守住规则的地方，比如同类内部调用 @Transactional 方法、在 @PostConstruct 上加事务、在事务方法内部加锁导致锁比提交先释放，这些都整理在 质量与问题 里。

    降级清单

    • 出题：简历题和方向题互为降级，都失败用兜底题。
    • 评估：批次失败按 0 分兜底，汇总失败退回批次结论拼接。
    • RAG：查询改写失败用原问题；带过滤条件的检索失败时，改为不带过滤多取三倍结果再在内存里过滤。
    • 语音：上下文摘要失败沿用旧摘要；单句合成失败跳过该句，全部失败再用整段文本合成一次。
    • 简历分析：模型失败时返回一份“分析出错”的 0 分报告。这条降级有副作用，会让重试机制失效，见 质量与问题。
