Agent 专题 · 改造方案

Agent 化改造：先修地基，再给模型决策权

这一页给出把项目往 Agent 方向推进的完整方案：先用一两天修掉会让 Agent 能力失真的地基问题，再依次做追问决策 Agent、Agentic RAG、MCP、多评委评估和长期记忆，并用评测和可观测把每一步的效果量化。每个方案都写明动机、设计、关键代码、风险和面试讲法；文中的代码草图都在与项目相同的 Spring AI 2.0.0 上编译通过，放在 project-analysis-site/lab/。

改造原则

  1. 先修地基，再加自主性：工具回合丢消息（A01）、护栏误伤（A02）、重试放大（A03）、摘要空转（A04）不修，任何 Agent 化都建立在会丢上下文、会误判、会放大成本的链路上。
  2. 每一步都可评估：先有指标和金标集，再改 Prompt、换模型、加工具。没有 L5，所有改进都只能凭感觉。
  3. 给决策权，也给边界：工具最小权限、每轮预算、循环硬上限、结构化的决策输出、人随时可以接管。
  4. 时延敏感的路径少用工具：语音这类实时链路优先“代码预取 + 直接注入”，工具留给文字模式和异步任务。
  5. 可回退：每项改造都挂在开关后面，新旧两条路径可以灰度对比。

第 1 步：追问决策 Agent

动机：现在的追问是出题时一次性定好的：文字面试每道主问题的追问数由配置固定（默认 1 个，最多 2 个），题库面试从追问池里随机抽取，都与候选人实际怎么回答无关；语音面试虽然是自由对话，但没有结构化的决策和证据。目标是在每次回答之后，由模型决定“追问 / 下一题 / 收尾”，并把判断依据记录下来，供最终报告引用。

设计决策

决策点选择理由
输出结构化 NextAction：枚举动作 + 一句要说的话 + 理由可校验、可统计、可回放；一段自由文本无法判断 Agent 做了什么决定
工具两个只读 + 一个幂等写只读工具可以放心重试；写工具以题号为键覆盖，重放不会重复
终止输出决策即结束；工具预算 3 次；模型请求硬上限 4 次两道保险，软预算引导模型收尾，硬上限兜底（E6）
上下文人设进系统提示词；对话记录进用户消息并包数据边界可信与不可信分开，正好是 A06 的反面
实时性文字模式直接使用；语音模式由代码预取参考要点、与 ASR 定稿并行，Agent 只做决策不做检索每次工具调用多一次模型往返
评分证据由 Agent 记录，总分仍由统一评估引擎计算决策和评分解耦，一个出错不会拖垮另一个
规则兜底同一道题最多追问 2 次，由代码判断“追问多少次”是产品规则，不交给模型
工具集（节选自 lab/agent/InterviewerTools.java）
@Tool(description = "查询某个考察类目的参考要点，用来判断候选人的回答遗漏了什么。只读，不要用它出新题。")
public String lookupReference(
    @ToolParam(description = "类目 key，例如 REDIS、RAG、MCP_PROTOCOL") String category) {
  if (!spend()) {
    return BUDGET_EXHAUSTED;                       // 机器可读的信号，引导模型直接给出决策
  }
  String points = references.keyPoints(category);
  return points == null ? "NOT_FOUND: 没有该类目的参考要点" : truncate(points, 1500);
}

@Tool(description = "记录对当前题目的评估证据和 0-100 分，同一题重复记录时以最后一次为准。")
public String recordObservation(
    @ToolParam(description = "题目序号，从 0 开始") int questionIndex,
    @ToolParam(description = "引用候选人原话的证据，50 字以内") String evidence,
    @ToolParam(description = "0 到 100 的整数分") int score,
    ToolContext toolContext) {                      // 会话 ID 走 ToolContext，不暴露给模型
  if (!spend()) {
    return BUDGET_EXHAUSTED;
  }
  if (score < 0 || score > 100) {
    return "INVALID_ARGUMENT: score 必须在 0-100 之间";   // 参数错误也回给模型，让它自行修正
  }
  String sessionId = String.valueOf(toolContext.getContext().get("sessionId"));
  observations.put(questionIndex, new Observation(sessionId, questionIndex, truncate(evidence, 80), score));
  return "OK";
}
决策入口（节选自 lab/agent/InterviewerAgent.java）
public InterviewerAgent(ChatModel chatModel, int maxModelCallsPerTurn) {
  this.chatClient = ChatClient.builder(chatModel)
      // 不手动注册 ToolCallingAdvisor，交给框架自动注册（保留完整历史）
      .defaultAdvisors(new LoopGuardAdvisor(maxModelCallsPerTurn, WRAP_UP_JSON))
      .build();
}

public NextAction decide(String sessionId, String persona, String transcript, InterviewerTools tools) {
  return chatClient.prompt()
      .system(persona + DECISION_RULES)            // 可信内容：人设与决策规则
      .user(transcript)                            // 不可信内容：对话记录（生产中包数据边界）
      .tools(tools)
      .toolContext(Map.of("sessionId", sessionId))
      .advisors(LoopGuardAdvisor.newBudget())      // 每次调用一个新的循环计数器
      .call()
      .entity(NextAction.class);
}

风险与评估

  • 过度追问：代码规定同一题最多追问 2 次，超过就强制 NEXT_QUESTION。
  • 打分漂移：Agent 记录的分数只作为证据，最终分数仍走统一评估，两者差异过大时标记人工复核。
  • 时延与成本：文字模式每轮 2–3 次模型请求；用 token 统计 Advisor 按场景看成本，语音模式靠预取把工具调用移出关键路径。
  • 怎么证明它比固定追问好：录一批真实面试片段，人工标注“这里该追问什么”，看 Agent 的追问是否指向被遗漏的要点（命中率）；同时看平均工具调用数、循环保护触发率和每轮时延。

第 2 步：Agentic RAG

现在的 RAG 是一条固定的提示链：改写 → 检索 → 生成，只检索一次，没有关键词召回、没有重排、没有引用，拒答靠关键词探测。升级分六处：

  1. 检索决策：“谢谢”“好的”这类消息不检索，用代码规则加一个小模型分类，省一次改写和一次向量检索。
  2. 查询分解：复合问题拆成子问题并行检索，比如“对比 HNSW 和 IVFFlat 的召回与内存”拆成两路。
  3. 混合召回：pgvector 向量检索 + 关键词检索，用倒数排名融合（RRF）合并。PostgreSQL 自带的全文检索不会切分中文，需要 zhparser、pg_jieba 这类分词扩展，或者退一步用 pg_trgm 做近似匹配。
  4. 重排：对融合后的前 20–30 段用重排模型精排，再取前 5–8 段进上下文。
  5. 带引用的结构化回答：要求模型输出答案、引用的片段编号，以及一个“资料是否足够”的布尔字段，取代现在按关键词判断拒答的探测窗口。
  6. 自检与纠正：每条引用都必须能在检索结果里找到；“资料不足”时换一种写法再检索一次，最多一次，仍然不足就如实说明。
倒数排名融合（节选自 lab/agent/RankFusion.java）
public static List<String> fuse(int k, int topN, List<String>... rankings) {
  Map<String, Double> scores = new HashMap<>();
  for (List<String> ranking : rankings) {
    for (int rank = 0; rank < ranking.size(); rank++) {
      // 只看名次不看分数，余弦相似度和全文检索得分不需要归一化
      scores.merge(ranking.get(rank), 1.0 / (k + rank + 1), Double::sum);
    }
  }
  return scores.entrySet().stream()
      .sorted(Map.Entry.<String, Double>comparingByValue(Comparator.reverseOrder())
          .thenComparing(Map.Entry.comparingByKey()))
      .limit(topN)
      .map(Map.Entry::getKey)
      .toList();
}

评测：准备一批“问题 + 标注的相关片段”，检索看 recall@k 和 MRR；生成看引用是否可验证、回答是否被引用片段支持；再统计拒答率。现在按长度调整阈值的经验参数，也应该放到这套评测上重新校准。

第 3 步：MCP

项目自带的参考把几个容易混淆的概念排成一条线：Function Calling 是模型能力，MCP 是连接工具与数据的协议标准，Skills 是更上层的能力封装。放到这个项目里：

概念是什么解决什么本项目
Function Calling模型输出结构化的调用意图让模型“说出”要调用什么Skill 工具走的就是它
MCP基于 JSON-RPC 2.0 的协议，定义 Host、Client、Server 与工具、资源、提示词等能力工具和数据只实现一次，任何支持 MCP 的宿主都能接入没有
SkillsSKILL.md 形式的能力包，渐进式披露把“怎么做一类事”的知识打包给 Agent10 个面试方向

方向一：把题库暴露成 MCP Server

把“抽题”“核对答案要点”做成 MCP 工具，用户就可以在 Claude Desktop、IDE 里的 Agent 等任意 MCP 宿主中直接练习。Spring AI 的 MCP Server Starter（WebMVC 版本，传输协议可配置为 Streamable HTTP）会把容器里的 ToolCallbackProvider Bean 注册为 MCP 工具。

public List<Map<String, Object>> drawQuestions(String category, String difficulty, int limit) {
  int safeLimit = Math.max(1, Math.min(limit, 5));          // 服务端夹紧参数，不信任调用方
  return bank.draw(category, difficulty, safeLimit).stream()
      .map(q -> Map.<String, Object>of("id", q.id(), "question", q.question()))
      .toList();                                            // 不返回参考答案
}

@Bean
public ToolCallbackProvider questionBankTools(QuestionBankMcpTools tools) {
  return MethodToolCallbackProvider.builder().toolObjects(tools).build();
}

要守住的边界：只暴露 ACTIVE 状态的题目；抽题不返回参考答案，核对答案只返回命中和遗漏的要点；每个客户端单独鉴权和限流；调用写审计日志。传输方式上，stdio 适合本机进程（桌面工具拉起一个本地 Server），Streamable HTTP 适合远程、多客户端的部署，它取代了早期的 HTTP + SSE 传输。

方向二：作为 MCP Client 接入外部能力

比如接入 GitHub 的 MCP Server，读取候选人简历里写到的开源仓库 README 和目录结构，生成更贴近真实代码的深挖题。风险在于外部内容是不可信数据，可能携带间接注入：只给只读权限，结果截断后包数据边界，并且只在出题这类“输出会被结构化校验”的环节使用。

第 4 步：多评委与评审-优化

评委小组

同一批回答交给 2–3 个视角的评委（正确性、深度、表达），或同一个评委采样 3 次；由代码取中位数或加权；分歧超过阈值的题标记人工复核。成本和时延约为原来的 2–3 倍，适合放在异步评估里。

题库的评审-优化循环

生成器出草稿 → 评审检查重复题、元信息题、能否由资料回答、参考答案与资料是否一致 → 生成器按意见修改，最多 2 轮；评审不通过的保持草稿状态，人只复核这部分。

什么时候不该用多 Agent：单个 Agent 加好的工具能解决的，就不要拆。多 Agent 的成本、时延和调试难度成倍增加；一致性靠“共享状态 + 编排者做最终裁决”，而不是让 Agent 之间自由对话。项目自带的参考里提到的“编排者-子 Agent”模式，在这里就是“代码编排 + 多个评委并行 + 代码汇总”，编排者甚至不需要是模型。

第 5 步：长期记忆与个性化练习

前提是先有用户体系（项目目前没有）。在此基础上，每次评估后更新一张学习者画像表：

字段来源用途

最近遗漏的要点知识库面试的 keyPoints 对照、Agent 记录的证据作为出题提示，追问优先落在这些点上

隐私上只存聚合统计和要点，不存回答原文，并提供删除入口。这样“记忆”不再只是去重，而是真正改变下一次面试的内容。

可观测怎么补

  • 在工具循环内侧挂 TokenUsageAdvisor，按 Provider 和场景统计输入、输出、缓存命中 token 和真实的模型请求次数（E7 验证了计数准确）。
  • 给循环保护触发、输出护栏拦截、结构化降级各加一个计数器，这三个数就是 Agent 健康度的早期信号。
  • 引入 micrometer-tracing 和 OpenTelemetry 导出，Spring AI 已经为 ChatClient、每个 Advisor、模型调用和工具执行生成了 Observation，接上就能看到完整的调用树。
  • 语音补一个“首段音频到达浏览器”的端到端时延，由前端上报。

用 Claude Code 推进的提示词

第 0 步：修地基
背景：project-analysis-site/lab 里的实验 E1、E3、E4、E5 复现了四个问题：默认配方工具回合丢失用户消息、语音摘要模板变量不替换、结构化输出最坏请求 8 次、SafeGuard 误伤候选人回答。

请按以下顺序处理，每一步先写失败的测试（RED），再做最小修改（GREEN），最后跑 ./gradlew :app:test --no-daemon：
1. LlmProviderRegistry：结构化与 RAG 调用不再挂 Skill 工具；删除手动注册的 ToolCallingAdvisor，交给 ChatClient 自动注册。测试：用一个第一轮请求工具的假 ChatModel，断言第二轮消息包含 USER 与带 tool_calls 的 ASSISTANT。
2. voice-interview-context-summary.st：占位符改为花括号。测试：渲染结果包含两个变量的值。

面试这样说

我给这个项目做 Agent 化的顺序是：先修地基，再建尺子，最后才给模型决策权。地基是工具回合丢消息、护栏误伤、重试放大、摘要模板空转这四个问题，每个都有最小实验复现；尺子是评委一致性和 RAG 召回两套金标集；然后才做追问决策 Agent，它输出结构化的动作，只有两个只读工具和一个幂等写工具，每轮有工具预算和模型请求上限，证据写进报告但总分仍由评估引擎计算。这样每一步都能用数据说明它比原来好。
