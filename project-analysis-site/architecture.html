    项目解析 · 架构

    整体架构与技术选型

    单体 Spring Boot 后端 + React 单页应用，外加三个基础组件（PostgreSQL、Redis、S3 兼容存储）和一组可切换的大模型服务。这一页讲清楚：进程之间怎么通信、代码怎么分层、一次请求怎么流动、数据存在哪里，以及每个技术为什么选它、放弃了什么。

    运行时全景

    下图是 Docker Compose 部署后的运行时视图，箭头上写的是通信方式。后端对外只有两个入口：经 Nginx 反向代理的 HTTP（普通接口和 SSE 流式接口都走这里），以及语音面试用的 WebSocket。后者目前由前端直接连到 8080 端口，没有经过 Nginx，这是部署上的一个缺口，质量与问题 一页有详细说明。

    分层与包结构

    后端是一个 Gradle 单模块工程，包根是 interview.guide。它没有按“controller / service / dao”横向切包，而是先分出通用能力、技术基础设施和业务模块三大块，业务模块内部再按 MVC 分层。

    包职责代表类
    common/ai大模型接入与治理：多 Provider 注册表、结构化输出执行器、Prompt 净化、Skill 工具配置LlmProviderRegistry、StructuredOutputInvoker、PromptSanitizer
    common/annotation、aspect可重复的 @RateLimit 注解与 AOP 切面RateLimitAspect + rate_limit_single.lua
    common/asyncRedis Stream 生产者、消费者模板基类AbstractStreamProducer、AbstractStreamConsumer
    common/evaluation文字、语音、知识库三种面试共用的评估引擎UnifiedEvaluationService
    common/exception、result错误码、业务异常、全局异常处理、统一响应ErrorCode、GlobalExceptionHandler、Result<T>
    common/config、constant、transaction类型安全配置、CORS、S3、OpenAPI、Stream 常量、小事务执行器TransactionalExecutor、AsyncTaskStreamConstants
    infrastructure/file文件类型识别、解析、清洗、哈希、对象存储DocumentParseService、FileStorageService
    infrastructure/redis、export、mapperRedis 操作封装、面试会话缓存、PDF 导出、MapStruct 映射器RedisService、InterviewSessionCache、PdfExportService
    modules/*六个业务模块：resume、interview、knowledgebase、voiceinterview、interviewschedule、llmprovider每个模块自带 Controller、service、repository、model，有异步任务的再带 listener

    约定写在 AGENTS.md 和 .claude/rules/backend.md 里，代码基本遵守：

    • Controller 只做路由、参数校验、限流注解和委托；业务编排在 Service；@Transactional 只放在 Service 的公开方法上，事务尽量小。
    • Entity 不直接返回前端，统一转成 record 形式的 DTO；重复的映射用 MapStruct 生成（ResumeMapper、InterviewMapper、KnowledgeBaseMapper、RagChatMapper），简单的一次性复制允许 BeanUtils。
    • 配置全部走 @ConfigurationProperties，不在 Service 里散落 @Value。提交 f87f435 专门做了一次清理，并用 grep 扫描确认 @Value、Executors.new、RuntimeException 为零。
    • 依赖通过构造器注入，配合 Lombok 的 @RequiredArgsConstructor。

    模块之间并不完全隔离，读代码时要注意几处横向依赖：简历删除会调用面试模块的持久化服务级联删除会话；知识库面试直接复用 InterviewSessionService 创建会话；简历分析结果的 DTO ResumeAnalysisResponse 放在了 interview 包里。这些是单体项目常见的“顺手依赖”，面试时被问到模块边界可以拿来当例子。

    统一约定：响应、错误码与异常

    HTTP 200 + 业务码

    所有接口返回 Result<T>（code、message、data），包括出错的时候：全局异常处理器统一用 @ResponseStatus(HttpStatus.OK) 返回，靠 code 区分成功（200）和各类失败。前端 Axios 拦截器据此统一解包或抛错。

    这种约定的好处是前端处理简单、错误信息总能带到页面上；代价是网关、监控和浏览器开发者工具无法从 HTTP 状态码识别失败，SSE 和文件下载这类“不是 JSON”的响应还要额外判断（前端为此专门写了 Blob 和流式响应里的错误识别，见 前端工程）。面试被问“为什么不用 HTTP 状态码”时，可以把这两面都讲出来。

    全局异常处理

    GlobalExceptionHandler 按异常类型分别处理：业务异常原样返回码和消息；参数校验异常拼接字段错误；上传超限单独提示；AI 调用的网络异常用 Java 21+ 的 switch 模式匹配按 cause 细分（SocketTimeoutException 映射为“超时”，消息里含 handshake 映射为“网络不稳定”），HTTP 客户端异常再按消息里的 401、429 映射到“密钥无效”“频率超限”；兜底的 Exception 只返回“系统繁忙”，详细堆栈留在日志里。这套写法是在 Java 25 升级时（4b96015）改成模式匹配的。

    源码节选 · common/exception/GlobalExceptionHandler.java
    @ExceptionHandler(ResourceAccessException.class)          // org.springframework.web.client
@ResponseStatus(HttpStatus.OK)
public Result<Void> handleResourceAccessException(ResourceAccessException e) {
    return switch (e.getCause()) {
        case SocketTimeoutException _ -> Result.error(ErrorCode.AI_SERVICE_TIMEOUT, "AI服务响应超时，请稍后重试");
        case null, default -> { ... "handshake" → 网络不稳定；否则 → 暂时不可用 }
    };
}

@ExceptionHandler(RestClientException.class)
@ResponseStatus(HttpStatus.OK)
public Result<Void> handleRestClientException(RestClientException e) {
    return switch (e.getMessage()) {
        case null -> Result.error(ErrorCode.AI_SERVICE_ERROR, "AI服务调用失败，请稍后重试");
        case String m when m.contains("401") || m.contains("Unauthorized") ->
            Result.error(ErrorCode.AI_API_KEY_INVALID, "AI服务密钥无效，请联系管理员");
        case String m when m.contains("429") || m.contains("Too Many Requests") ->
            Result.error(ErrorCode.AI_RATE_LIMIT_EXCEEDED, "AI服务调用过于频繁，请稍后重试");
        default -> Result.error(ErrorCode.AI_SERVICE_ERROR, "AI服务调用失败，请稍后重试");
    };
}
    这两个分支在 Spring AI 2.0 下接不到模型调用的异常

    它们捕获的是 Spring 的 RestClientException 家族，这是 Spring AI 1.x 底层用 RestClient 调模型时会抛的异常。项目现在的模型实例由 ApiPathResolver 用 OpenAI 官方 Java SDK（com.openai.client.OpenAIClient）构建。按项目完全相同的构建方式，指向一个本地假服务实测，异常类型是：

    假服务的行为实际抛出的异常是 RestClientException 吗假服务收到的请求数
    返回 401com.openai.errors.UnauthorizedException否1
    返回 429com.openai.errors.RateLimitException否3
    返回 503com.openai.errors.InternalServerException否3
    读超时com.openai.errors.OpenAIIoException ← SocketTimeoutException否3
    端口不通com.openai.errors.OpenAIIoException ← ConnectException否—

    所以错误码 7002（超时）、7004（密钥无效）、7005（频率超限）在整个代码库里只有这两个处理器会产生，而它们实际上接不到模型调用的异常。多数业务代码会先把异常包成 BusinessException（前端看到的是“简历分析失败：429: …”这类拼接原文的提示），没被包住的落进兜底分支，只显示“系统繁忙，请稍后重试”。修复是按 com.openai.errors 的类型重写这两个处理器。

    第二列的请求数揭示了另一件事：OpenAI Java SDK 自带重试，对 429、5xx 和网络超时默认再试 2 次（请求头里的 x-stainless-retry-count 依次是 0、1、2，间隔约 0.5 秒、1 秒）。spring.ai.retry.max-attempts: 1 关掉的只是 Spring AI 自己的重试模板，管不到 SDK 这一层，而 ApiPathResolver 构建客户端时也没有设置 maxRetries。

    一次请求怎么走：以上传简历为例

    这是项目里最典型的“同步阶段只做快且确定的事，慢调用丢给异步”的链路，面试讲架构时可以拿它串起大部分组件。

    1. 前端上传：multipart/form-data 经 Nginx 转发，Axios 对上传单独设置 5 分钟超时。
    2. 限流：@RateLimit 切面在进入 Controller 前执行 Lua 脚本，全局和单 IP 各限每秒 5 次。
    3. 校验：文件非空、不超过 10MB；用 Tika 基于文件内容识别 MIME 类型，而不是相信扩展名或请求头，再和白名单（PDF、DOC、DOCX、TXT）比对。
    4. 去重：计算文件内容的 SHA-256，命中 resumes.file_hash 唯一索引就直接返回历史分析结果，并把访问次数加一。
    5. 解析：Tika 提取正文（关闭嵌入资源解析，PDF 按坐标排序文本），再做文本清洗；提取不到文字时提示“可能是扫描版 PDF”。
    6. 存原文件：上传到 RustFS / MinIO，对象键为 resumes/年/月/日/UUID_拼音文件名。
    7. 落库：写入 resumes 表，分析状态为 PENDING。
    8. 投递：向 resume:analyze:stream 发送一条消息（简历 ID、正文、重试次数 0），投递失败时把状态直接改成 FAILED。
    9. 立即返回：接口返回 PENDING，前端跳到简历库，每 3 秒轮询一次列表。
    10. 异步分析：消费者线程拉到消息，检查简历是否已删除或已完成，改为 PROCESSING，调用大模型做结构化评分，写入 resume_analyses，最后改为 COMPLETED 并 ACK；失败则重新入队，最多 3 次。

    数据模型

    共 16 张表，全部由 Flyway 的 V1__init_schema.sql 和 4 个增量脚本创建。按领域归类如下：

    领域表值得注意的设计
    简历resumes、resume_analysesfile_hash 唯一索引做内容去重；一份简历可以有多次分析记录，列表取最新一条；优势和建议以 JSON 文本存储
    面试interview_sessions、interview_answerssession_id 和 request_id 各有唯一约束；题目整体存在 questions_json；答案表 (session_id, question_index) 唯一，天然支持“同一题重复提交只更新”；会话状态和评估状态是两个独立字段
    知识库knowledge_bases、knowledge_base_questions、vector_store知识库行上同时承载向量化状态和题库生成任务的 8 个字段（状态、taskId、参数快照、计数、时间）；vector_store 是 Spring AI 的标准表结构（UUID、正文、JSON 元数据、vector(1024)），由 Flyway 建表并建 HNSW 余弦索引
    问答会话rag_chat_sessions、rag_chat_messages、rag_session_knowledge_bases会话和知识库多对多；消息带 message_order 和 completed 标记，用于流式输出前先占位
    语音面试voice_interview_sessions、voice_interview_messages、voice_interview_evaluations评估表 session_id 唯一；上下文摘要复用消息表，以 message_type = SUMMARY 的特殊行保存，序号取负数编码“已覆盖的轮次数”，避免新增表
    模型配置llm_provider_config、llm_global_settingAPI Key 以密文 + nonce 两列保存；全局设置是单例行，保存默认聊天和默认向量 Provider
    日程interview_schedule状态用 CHECK 约束限定为四个枚举值

    几个可以主动讲的取舍：

    • JSON 存在 TEXT 列里（题目、优势、建议、参考答案等）。读写简单、结构可变，代价是不能在数据库里按字段查询或建索引。如果将来要做“按知识点统计错题”，就需要拆表或改成 JSONB。
    • 状态字段 + CHECK 约束。每个异步任务都有 *_status 和 *_error 两列，前端轮询这两列即可展示进度和失败原因。
    • 物理外键不一致。简历、面试、知识库、问答会话之间有外键；语音会话对简历只有逻辑关联。知识库和题目之间有外键但没有级联删除，这恰好导致了一个删除缺陷，见 质量与问题。
    • vector_store.metadata 是 JSON 而不是 JSONB。项目用 metadata->>'kb_id' 过滤和删除，数据量大时这类过滤无法走 GIN 索引。

    技术选型与取舍

    选择替代方案为什么这样选代价 / 边界
    PostgreSQL + pgvectorMilvus、Elasticsearch、Qdrant业务数据和向量放一个库，少运维一个组件；向量和业务表可以在同一个事务里删改（本项目的“影子向量提升”就依赖这一点）千万级向量以上、复杂混合检索时不如专用向量库；维度写死在表结构里，换模型要迁移
    Redis StreamKafka、RabbitMQ、RocketMQRedis 已经用于缓存和锁，Stream 提供消费者组、ACK、pending 列表，足够支撑五类后台任务；README 明确写了“不想引入太多组件”没有原生延迟队列和死信队列，重试靠重新 XADD；持久化依赖 Redis 的 AOF/RDB 配置
    RedissonLettuce、Jedis现成的分布式锁（看门狗）、Stream、脚本 API4.0 版本在空结果时会抛 ClassCastException，项目里专门 catch 兼容
    Spring AI + OpenAI 兼容协议各厂商 SDK、LangChain4j国内主流模型都提供 OpenAI 兼容接口，一套 OpenAiChatModel 换 base-url 即可接入；ChatClient、Advisor、结构化输出、VectorStore 开箱即用“兼容”不等于完全一致，工具调用消息的校验差异曾导致出题失败（见 Skill 演进）
    虚拟线程（Java 25）WebFlux 全响应式请求处理大量阻塞在大模型和数据库 IO 上，虚拟线程让同步写法也能撑高并发；并行出题和语音管线也跑在虚拟线程上SSE 部分仍用了 Reactor 的 Flux；锁内阻塞、synchronized 固定载体线程等问题需要留意
    Flyway + ddl-auto: validateHibernate 自动建表表结构变更可审计、可回放；启动时 Hibernate 校验实体与表一致测试环境用 H2 + create-drop，和生产方言不同，PostgreSQL 特有 SQL（如 JSON 操作）测不到
    MapStruct手写转换、BeanUtils编译期生成代码，类型安全、零反射JSON 字段仍要在 Service 里手动序列化，映射器里用默认方法补
    Apache TikaPDFBox + POI 分别处理一个入口自动识别并解析多种格式扫描件没有文字层时无能为力，需要 OCR
    对象存储（S3 协议）本地磁盘无状态部署、可切换到云厂商；强制 path-style 访问避免桶名进域名导致的 DNS 问题多一个组件；删除时需要处理“数据库删了、文件没删掉”的补偿
    SSE（RAG 问答）WebSocket单向推送，基于 HTTP，易于穿过代理需要关闭代理缓冲，否则打字机效果会变成成批输出
    WebSocket + 服务端中转音频（语音面试）WebRTC、端到端语音模型实现简单，服务端可以统一做回声过滤、上下文管理和计量音频多一跳，端到端延迟偏高；README 已把 WebRTC 列为待办
    Prompt 模板文件（StringTemplate）硬编码字符串Prompt 与代码分离，便于迭代和审查模板语法用 {}，写 JSON 示例或误用 <var> 时容易出错（项目里两种问题都出现过）

    部署拓扑

    根目录的 docker-compose.yml 编排 6 个服务，依赖关系用健康检查串起来：

    • postgres：pgvector/pgvector:pg16 镜像，首次启动执行 init.sql 创建 vector 扩展，pg_isready 做健康检查。
    • redis：redis:7，redis-cli ping 健康检查。
    • minio 与 createbuckets：后者是一个“初始化容器”，等 MinIO 健康后用 mc 幂等地创建桶，完成后退出。
    • app：多阶段构建。第一阶段在 JDK 25 镜像里先只复制 Gradle 配置并预下载依赖（利用镜像层缓存），再复制源码执行 bootJar；第二阶段只把 jar 拷进 JRE 镜像。它等待前面四个服务都“健康”或“成功完成”才启动。
    • frontend：Node 构建后放进 Nginx。Nginx 配置了单页应用的 try_files 回退、/api 反代（读写超时 300 秒，匹配大模型的长耗时）、50MB 请求体上限和 gzip。

    本地开发用 docker-compose.dev.yml 只起 PostgreSQL、Redis、RustFS 三个依赖，后端用 ./gradlew :app:bootRun 运行。build.gradle 里写了一段逻辑，把根目录 .env 逐行读进 bootRun 的环境变量，同时把 JVM 的文件与控制台编码固定为 UTF-8（解决 Windows 下中文日志乱码）。后端启动时还会检查对象存储桶，不存在就创建，409 冲突视为已被其他进程创建。

    设置页修改的聊天 / 向量 Provider 保存在数据库里，API Key 加密存储。语音服务（ASR/TTS）的配置走的是另一条路：修改后立即改写内存中的配置对象并热加载语音服务，同时写入 ~/.interview-guide/ 下的 YAML 和 env 文件。但应用启动时并不读取这两个文件，所以重启后语音配置会回到 application.yml 的值，而 DashScope Key 却以明文留在了 env 文件里。启动时会检查这两个路径的父目录是否可写，不可写直接启动失败。

    部署上的缺口

    语音 WebSocket 地址由后端拼成 ws://localhost:8080/... 返回给前端，Nginx 也没有配置 /ws 的 Upgrade 代理，所以远程部署时语音面试连不上；/api 反代没有关闭 proxy_buffering，SSE 流式回答会被 Nginx 攒批。另外项目没有登录和多用户体系（语音会话的用户 ID 固定为 default）。这些都是“如果上线你会怎么改”的好素材。

    配置体系

    application.yml 里几乎每个可调参数都写成 ${环境变量:默认值} 的形式，敏感信息只放在 .env。主要分组：

    • spring.*：开启虚拟线程；数据源；JPA 只做校验；Flyway 开启并允许对已有库打基线；上传上限 50MB（简历的 10MB 限制在业务层判断）；Redisson 连接池 64、最小空闲 10；spring.ai.retry.max-attempts: 1 关闭框架自带重试；pgvector 使用 HNSW、余弦距离、1024 维，并且不让 Spring AI 自己建表。
    • app.ai.*：默认聊天与向量 Provider、各 Provider 的地址、模型和 Key、加密密钥要求、Advisor 开关（工具调用、会话记忆、日志、SafeGuard）、结构化输出的重试策略、RAG 的改写开关和按问题长度划分的 TopK 与相似度阈值。
    • app.interview.*：每道主问题的追问数（默认 1）、评估分批大小（默认 8）。
    • app.voice-interview.*：阶段时长、Qwen3 ASR/TTS 参数（采样率、静音断句阈值 2000ms、音色）、流式推送节奏、TTS 并发与超时、开场音频预热开关。
    • management.*：暴露 health、info、metrics、prometheus 端点，并开启存活/就绪探针。

    这些配置都绑定到 @ConfigurationProperties 类（例如 LlmProviderProperties、VoiceInterviewProperties、KnowledgeBaseQueryProperties），代码里拿到的是强类型对象。

    可观测性

    除了 Actuator 自带的 JVM、HTTP、连接池指标，项目自己埋了两组业务指标，都通过 Micrometer 注册，可以被 Prometheus 抓取：

    • 结构化输出：app.ai.structured_output.invocations、attempts、latency，标签是调用场景和成功/失败。场景名先规范化成小写下划线并限制 48 个字符，避免标签基数失控。但规范化会把所有非 [a-z0-9_] 字符换掉，而调用方传的场景名全是中文，实际只剩 unknown 和 jd 两个标签值，按场景拆分指标做不到，见 AI 底座 · 结构化输出。
    • 语音面试：大模型首 token 延迟、大模型总耗时、TTS 耗时、ASR 合并等待时间、单轮总耗时、轮次成功/失败计数、TTS 空音频计数。这些是调优语音延迟的依据。

    缺少的部分：没有链路追踪，日志不是结构化格式，异步任务的积压量（Stream 长度、pending 数）没有暴露成指标。如果被问“怎么监控这个系统”，可以从这三点展开。
