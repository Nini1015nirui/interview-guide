    项目解析 · 业务模块

    业务模块逐个拆解：每个功能背后的真实链路

    前几页讲的是横切的底座：模型接入、异步模板、一致性。这一页按功能走一遍，从用户点下按钮开始，到数据落到哪张表、哪一步调模型、失败了会怎样。每个模块最后都列出读源码时发现的实现细节和问题，面试官问“这里有什么可以改进的”时，这些就是你的答案。

    模块总览

    六个业务模块的骨架是一样的：Controller 只做路由和校验，业务编排在 Service，数据库读写再单独拆出一个 PersistenceService，这样事务边界可以收得很小。凡是要调模型且结果不必马上拿到的，都落库后投递到 Redis Stream，前端按 3 秒间隔轮询状态字段。

    模块主要表异步管线调模型的地方前端页面
    简历resumes、resume_analyses简历分析五维评分与建议上传页、简历库、简历详情
    文字面试interview_sessions、interview_answers面试评估出题（1–2 次）、评估（分批 + 汇总）、JD 解析模拟面试入口、答题页、面试记录
    知识库与问答knowledge_bases、vector_store、rag_chat_*向量化查询改写、流式回答、Embedding知识库上传与管理、问答助手
    题库面试knowledge_base_questions，会话复用 interview_sessions题库生成生成题目、参考答案与追问题库页、题库面试入口
    面试日程interview_schedule无（每小时定时任务）邀约文本解析兜底日历页
    系统设置llm_provider_config、llm_global_setting无连通性测试设置页

    语音面试单独成页，见 语音面试。

    简历管理

    上传链路

    1. 基本校验：文件非空，大小不超过 10MB。
    2. 按内容识别类型：用 Tika 读文件头的魔数（文件名只作辅助），不信任浏览器上报的 Content-Type，再和配置里的白名单（PDF、DOC、DOCX、纯文本）比对。改个扩展名伪装的文件过不了这一关。
    3. 按内容去重：对整个文件算 SHA-256，命中已有记录就把访问次数加一，直接返回最近一次分析结果，并提示“检测到相同简历，已返回历史分析结果”。同一份简历改个文件名再传，也会被识别出来。
    4. 解析正文：Tika 自动识别解析器，只取正文（上限 500 万字符）；禁用嵌入文档解析，避免把图片引用、临时文件路径抽出来；PDF 关闭内嵌图片提取、按坐标排序文本，改善双栏简历的阅读顺序。
    5. 清洗：去掉控制字符、整行的图片文件名、图片链接、file: 协议路径和分隔线，统一换行符，去掉行尾空白，把三个以上连续换行压成一个空行。清洗后为空，就提示“请确保文件不是扫描版 PDF”，项目没有做 OCR。
    6. 存原件：对象键形如 resumes/2026/08/14/1a2b3c4d_ZhangSanJianLi.pdf，按日期分目录，前缀 8 位随机串防重名，中文文件名转成大驼峰拼音，其他特殊字符替换成下划线，规避 S3 对键名的兼容问题。
    7. 落库并投递：状态写 PENDING 后提交事务，再把“简历 ID + 正文”写入分析 Stream，接口立即返回。前端拿到 ID 后开始轮询。

    分析与报告

    分析 Prompt 的人设是“10 年以上经验的技术架构师兼人才顾问”，要求做三件事：纠正不规范的技术名词（如 mysql 写成 MySQL）、挑 2–3 条项目经历按 STAR 法则给出“原句 vs 优化句”、对平庸的技术方案给出替代建议。评分是固定权重的五个维度：

    维度满分看什么
    项目经验40是否避开烂大街项目，有没有复杂问题排查、业务闭环和量化结果
    技能匹配度20技术栈表述是否专业，“了解 / 熟悉 / 熟练掌握”是否分清
    内容完整性15模块顺序是否合理
    结构清晰度15技术名词大小写是否规范
    表达专业性10语言是否简洁

    用户 Prompt 里还附了一份“技术优化基准”表（多级缓存、Lua 原子操作、CompletableFuture 编排、Canal 同步、分库分表等参考表达），让建议有统一的“好简历长什么样”的锚点。简历正文用固定的“简历内容开始 / 结束”分隔符包起来，并声明其中是数据而不是指令。输出经结构化执行器校验后，优势和建议以 JSON 存进 resume_analyses，前端用雷达图展示五个维度的得分。每次分析都是新的一行，所以简历详情页能看到分析历史，以及用这份简历做过的所有面试。

    导出 PDF 用 iText 8，内嵌了朱雀仿宋字体（强制嵌入，否则在没装中文字体的机器上会乱码），导出前去掉 emoji 这类字体里没有的符号。“重新分析”时优先用库里缓存的正文，没有再从对象存储下载重新解析，改状态和投递分两步：先用小事务把状态改回 PENDING 并提交，再投递。

    实现细节与问题

    • 降级吞掉了重试：模型调用失败时，评分服务返回一份 0 分、摘要为“分析过程中出现错误”的报告，消费者把它当成功保存并标记 COMPLETED。Stream 模板的三次重试、FAILED 状态和前端的“重新分析”入口都因此失效，用户看到的是一份 0 分报告。
    • 列表页 N+1：简历列表对每份简历再查一次最新分析、再查一次面试记录，100 份简历就是 201 条 SQL，违反了项目自己“不要循环调用 DB”的规则。
    • 删除顺序和知识库相反：简历是先删对象存储文件，再分两个事务删面试和简历记录；如果后面失败，会留下没有原件的记录。知识库删除则是“先删数据库，提交后再清理文件”，后者更合理。
    • 并发上传同一文件：两个请求同时通过去重检查，第二个在插入时撞上唯一索引，用户看到“保存简历失败”，对象存储里还多了一个孤儿文件。可以在唯一索引冲突时回查已有记录并删除刚上传的文件。
    • 错误信息透传：解析失败时把异常原文拼进提示返回给前端，暴露了内部细节。
    • Prompt 小瑕疵：评分细则里写的字段名是 projectTechDepth，JSON 格式说明里却是 projectScore，靠结构化输出的 schema 兜住了。

    文字模拟面试

    入口在“模拟面试”页：选面试方向（10 个 Skill 或粘贴 JD 生成自定义方向）、难度（初级 / 中级 / 高级）、题量（界面提供 6、8、10、12 题）、是否带简历、用哪个模型。出题逻辑见 AI 底座 · 出题流程，幂等创建见 可靠性 · 刷新不重复出题，这里讲会话本身。

    会话生命周期

    • 创建：会话 ID 是 16 位十六进制串。带简历且没勾选“强制新建”时，先找这份简历未完成的会话（先查 Redis 索引，再查数据库），有就直接返回，这就是“继续上次面试”。
    • 作答：两种写法。“暂存”只保存当前题答案、不前进；“提交”保存答案并把当前题号加一，提交的是最后一题时会话变为 COMPLETED 并触发评估。两者都是先写数据库（答案按“会话 + 题号”唯一，重复提交只改同一行），再更新 Redis。
    • 提前交卷：已交卷或已评估的会话再交卷会被拒绝；否则置为 COMPLETED、评估状态 PENDING，然后投递。
    • 评估：消费者从 questions_json 还原题目、把答案表回填进去，按会话记录的模型调用统一评估引擎。知识库面试的题目自带参考答案和评分规则，会优先作为评估基线。
    • 写报告：一个事务里写会话的总分、评语、优势、改进建议和参考答案，并把每道题的分数、反馈、参考答案、要点写回答案表；没作答的题也补一行，分数为 0。
    • 查看：面试记录页把文字面试和语音面试合并展示，顶部是历次得分的趋势折线图；详情里有逐题得分、反馈和参考答案，可以导出 PDF 和删除（级联删除答案）。

    实现细节与问题

    • 校验注解没生效：创建请求上写了题量 3–20、方向不能为空的校验注解，但接口参数前漏了 @Valid，这些约束一条都不执行，出题服务里也没有截断题量。项目里其他写了校验注解的请求体都配了 @Valid，只有这一处漏掉。

    • 遗留的同步报告接口：GET /api/interview/sessions/{id}/report 仍然会在请求线程里把整场面试同步评估一遍并覆盖已有报告，没有限流。前端早已改成读异步结果，这个接口没有调用方，却是一个能被反复触发的昂贵操作，应该删除或改成只读。
    • 简历文本来自前端：出题用的简历正文是前端随请求传上来的，而评估时用的是数据库里 resumeId 对应的正文。两个来源在正常使用时一致，但后端其实没必要信任客户端传来的正文。
    • 吞掉的失败：没有幂等键的创建路径里，会话落库失败只打一条告警，这场面试就只存在 Redis 里，24 小时后消失；暂存答案失败也只打告警，前端以为保存成功。
    • 请求体用 Map：提交和暂存答案的接口用 Map<String, Object> 接参再强转，传错类型会变成 500，而不是清晰的参数错误。

    知识库与 RAG 问答

    上传

    和简历上传同一套流程，差别在三处：大小上限 50MB；类型判断是“MIME 在白名单里，或者扩展名是 .md / .markdown / .mdown”，因为 Markdown 常被识别成普通文本；正文不存数据库，只随消息发给向量化消费者，“重新向量化”时再从对象存储下载解析。上传时可以填名称和分类，列表页支持按分类筛选、搜索、排序和统计。

    向量化与影子写入

    分块用 Spring AI 的 TokenTextSplitter 默认配置（每块约 800 token，在标点处断开，块之间没有重叠），Embedding 按每批 10 块调用，这是 DashScope 接口的批量上限。真正值得讲的是“重新向量化”怎么做到失败不污染、过程中不停服：

    “影子写入”具体是怎么做到“检索看不到”的：检索时的过滤条件是 kb_id in ['7']，而新写入的每个分块，kb_id 字段先填的是一个不可能被查到的临时值。下面是一个分块的 metadata 在各阶段的真实形态（前三个字段是 Spring AI 的 TokenTextSplitter 自动加的）：

    走一遍：重新向量化知识库 7（jobId = 4c1e8f2a-…） 
    ① 分块：TokenTextSplitter 默认配置
   以仓库自己的 README.md 为例：19224 个字符 → 12 个分块（每块 863–2232 字符）→ 2 批 Embedding 调用
   注意第 1 块结尾是依赖表的某一行，第 2 块开头是表格的下一行：分块不重叠，也不认识 Markdown 结构

② 写入临时数据（vectorStore.add，每批 10 块，事务外）
   metadata = {"chunk_index":0, "total_chunks":12, "parent_document_id":"cbbc5273-…",
               "kb_id":"pending:7:4c1e8f2a-…",        ← 检索过滤 kb_id in ['7'] 匹配不到它
               "kb_target_id":"7", "kb_vector_job_id":"4c1e8f2a-…"}

③ 全部成功后，一个事务里执行两条 SQL（activateVectorJob）
   DELETE FROM vector_store
    WHERE metadata->>'kb_id' = '7'
       OR (metadata->>'kb_id_long' IS NOT NULL AND (metadata->>'kb_id_long')::bigint = 7);
   UPDATE vector_store
      SET metadata = (jsonb_set(metadata::jsonb, '{kb_id}', to_jsonb('7'::text), true)
                      - 'kb_vector_job_id' - 'kb_target_id')::json
    WHERE metadata->>'kb_vector_job_id' = '4c1e8f2a-…';
   提交后 metadata = {"chunk_index":0, "total_chunks":12, "parent_document_id":"cbbc5273-…", "kb_id":"7"}

③' 任何一步失败（比如第 2 批 Embedding 超时）
   DELETE FROM vector_store WHERE metadata->>'kb_vector_job_id' = '4c1e8f2a-…';
   旧的 kb_id='7' 的向量一行没动，检索照常工作

    这套机制来自提交 72aff88（“将知识库向量化改为临时任务提升，避免失败时污染正式检索数据”）。在它之前，重新向量化是“先删旧的再写新的”，写到一半失败，知识库就只剩一部分向量。实现上有两处小心思：元数据列是 json 类型，提升时先转 jsonb 用 jsonb_set 改 kb_id、删掉两个临时键，再转回 json；删除语句额外兼容了旧版本数据里的 kb_id_long 字段，并刻意避开 PostgreSQL 的 ? 操作符，因为它会和 JDBC 占位符冲突。

    问答链路

    • 为什么要改写：多轮对话里用户常问“那它的原理呢”，直接拿这句去检索什么也找不到。改写 Prompt 拿到最近的对话历史（助手回复截断到 200 字），输出一句适合检索的完整查询。改写结果和原问题都作为候选，按顺序检索，第一个有结果的胜出，防止改写跑偏。
    • 为什么按长度调参：两三个字的查询（例如“索引”）向量很“虚”，和相关段落的相似度普遍偏低，所以阈值放低、多取几条；长问题语义明确，少取几条、阈值抬高，减少噪声。中间档的分界值 12 写死在代码里，其他值都可配置。长度是去掉所有空白后的字符数，按 application.yml 实际生效的值：
      问题去空白长度档位TopK相似度阈值
      索引2短（≤ 4）200.18
      Redis 持久化机制10中（≤ 12）120.28
      RDB 和 AOF 在宕机恢复时各有什么取舍？20长80.28
      有一个实现细节：档位是按原始问题算的，不是按改写后的查询。多轮对话里用户追问“那它呢”（3 个字），改写后已经是一句完整的查询，却仍然按“短查询”取 20 条、阈值 0.18，召回的噪声反而最多。
    • 多轮上下文：历史消息作为真正的对话消息传给模型，而不是拼进文本。取最近 10 条已完成的消息，实现上多查一条再丢掉最新的那条，因为当前这轮的用户消息已经先落库了（1bf8f1b）。
    • 流式与落库：发消息时先在一个事务里保存用户消息和一条“未完成”的助手占位消息，再开始流式输出；完成时写入完整内容，出错时保存已收到的部分或错误提示。会话支持改标题、置顶、更换关联的知识库，标题默认取知识库名。
    • Prompt 里的流式格式规范：系统提示词花了很大篇幅规定 Markdown 格式（## 后必须有空格、列表项独立成行等），因为流式渲染时格式不规范会导致前端边收边渲染出错。
    走一遍：会话里的第二个问题“那它的持久化呢？” 
    历史（最近 10 条已完成消息）：
  用户: Redis 为什么快？
  助手: Redis 快主要有三点：纯内存操作、单线程避免上下文切换、IO 多路复用……（截到 200 字）

   模型返回：Redis 的持久化机制有哪些
   候选查询 = [ "Redis 的持久化机制有哪些", "那它的持久化呢？" ]

   用第一个候选检索：kb_id in ['3', '5']，命中 5 条 → 直接用它，不再试第二个候选

   RDB 是某一时刻的内存快照……
   ---
   AOF 以追加方式记录每条写命令……
   ---文档内容结束---

   窗口内出现“没有找到相关信息 / 未检索到相关信息 / 信息不足 / 超出知识库范围 /
   无法根据提供内容回答”之一 → 丢弃模型输出，只推一句固定文案并结束
   否则把这 120 个字符一次性推出去，之后逐块透传

    一次问答因此是两次模型调用（改写 + 回答），检索没命中时是一次。改写的输入模板里 {question} 和 {history} 是直接上下拼接的，中间没有标题分隔，模型要自己判断“哪一行是问题、哪几行是历史”。

    RAG 部分可以深挖的问题

    学习资料触发护栏：问答走的是挂着 SafeGuard 的默认配方，关键词闸门会扫描检索到的资料；一份讲 Prompt 注入的学习笔记里只要出现“忽略之前的指令”，相关问题就会被固定回复“抱歉，我只能协助面试相关的任务”挡掉（实验 E5）。断开连接的占位消息：流式接口只处理了“完成”和“出错”，没处理“取消”。用户中途关页面，助手占位消息会永远停在未完成、内容为空。拒答判断会误伤：非流式接口只要整段回答里任何位置出现“信息不足”等 5 个短语之一，就整体替换成固定回复；流式接口只检查前 120 个字符。而用户提示词的回答要求里恰恰写着“如无相关信息，仅用 1-2 句说明信息不足”，等于教模型说出触发过滤的那个词。一个“前半段正常回答、最后一句说某方面信息不足”的回答，在非流式接口里会被整段吞掉，在流式接口里却能完整显示，两个接口对同一个问题的表现不一致。配置漂移：提交 1bf8f1b 把短查询阈值的代码默认值从 0.18 提到 0.25，但 application.yml 里仍写着默认 0.18，yml 优先，实际生效的还是 0.18。规模化：vector_store 只有 HNSW 向量索引，元数据上没有索引，按 kb_id 删除、提升、清理都是全表扫描；HNSW 先取近邻再按元数据过滤，目标知识库在全库里占比很小时召回会明显不足，可以考虑表达式索引、分区，或 pgvector 0.8 的迭代扫描。检索质量：分块没有重叠，没有关键词检索做混合召回，没有重排，回答也不标注出处。

    题库与题库面试

    这是项目里最新、也是一致性设计最用心的模块（2026 年 6–7 月的十几个提交）。流程是：知识库向量化完成 → 生成草稿题 → 人工审核、编辑、启用 → 按容量抽题面试 → 用题目自带的参考答案和评分规则评估。生成任务的状态机见 可靠性 · 题库生成状态机。

    生成：给模型什么上下文

    生成参数是难度（初级 / 中级 / 高级）、题量 1–30（默认 5）、每题追问 0–5（默认 2）、方向数 1–5。上下文不是把整份资料塞给模型，而是用四个“探针查询”在这个知识库里各取 4 个片段：

    • 核心概念、定义、背景、原理
    • 关键流程、步骤、方法、工作机制
    • 规则约束、条件、边界、例外、限制
    • 典型案例、常见问题、应用场景、最佳实践

    片段按文本去重，最多 12 个，拼起来截断到 5000 字，用随机分隔符包好。Prompt 里还会告诉模型这个知识库已有哪些方向（前 10 个及题数，引导复用方向名）以及同难度最近 20 道题（避免重复）。调用用的是不带工具的 plain 配方，结果走结构化输出。落库前逐题清洗：空题干跳过；题干做 Unicode 规范化、转小写、只保留字母数字后比较，重复的跳过并计数；方向为空时用知识库名；追问截断到请求的数量。每道题还记录了生成时用的上下文和知识库内容哈希。

    用四个固定的探针查询代替“随机取片段”，设计意图是在低成本下覆盖资料的不同侧面：概念题、流程题、边界题、场景题各有来源。但把真实数字代进去，这个意图基本落空了：

    5000 字符的截断让后三个探针几乎不起作用

    片段是按探针顺序收集的：先放“核心概念 定义 背景 原理”的 4 个结果，再放第二个探针的，以此类推，最后整体截到 5000 字符。而 TokenTextSplitter 默认每块约 800 token，中文资料一块通常有一两千个字符。用仓库里两份真实文档实测：README.md 分出的 12 块平均 1600 字符，docs/voice-interview-architecture.md 的 7 块平均 1479 字符，5000 字符都只能完整放下 3 块。也就是说，送进模型的上下文基本就是第一个探针的前 3 个结果，第二个探针最多露出半块，“流程 / 边界 / 场景”三个探针的结果被截掉了。“最多 12 个片段”只在资料很碎、每块很短时才成立。修法可以是每个探针只取 1–2 块并按探针轮流放，或者把上限按片段数而不是字符数来算。

    落库前的去重规则（buildEntities）也可以具体到代码：题干先做 Unicode NFC 规范化，再转小写，然后只保留 Character.isLetterOrDigit 为真的字符（汉字也算 letter，空格和标点被去掉）进行比较。所以“什么是 Redis 的 AOF？”和“什么是redis的AOF”被视为重复，第二道跳过并计入 skippedCount，完成消息就是“已生成 4 道题，跳过 1 道重复题”。

    题目状态与维护

    题目有四种状态：生成出来是草稿（DRAFT），人工确认后启用（ACTIVE），不想用了归档（ARCHIVED），还有一个预留的过期（STALE），代码里目前没有任何地方会把题目置为过期。只有 ACTIVE 的题会被抽进面试。题库页支持按状态和方向筛选、分页、批量选择、编辑题干和参考答案、手动新增题目。

    容量矩阵与严格抽题

    开始题库面试时，用户选方向（可不选，表示全部方向）、难度、主问题数 1–20、每题追问数 0–5。项目的原则是“严格满足，不静默降级”：凑不够就明确告诉用户差在哪。为了在用户点“开始”之前就知道能不能凑够，后端提供一个容量接口，返回一张矩阵：

    每题追问数满足条件的启用题要 5 道主问题时能否开始
    012可以
    112可以
    29可以
    34不够
    41不够
    50不够

    表中数字为示意。每一行的含义是“追问池里至少有这么多个有效追问的启用题有几道”；同时返回各方向的可用题数，按数量降序，前端据此禁用不可行的选项并给出提示。

    抽题时，先筛出“方向、难度匹配、状态启用、追问数够”的候选题，打乱后取前 N 道；每道题的追问再从追问池里随机取指定个数（局部 Fisher–Yates 洗牌，不改动原列表），让同一道题每次的追问组合不同。“局部洗牌”在代码里就是下面这几行：只需要前 count 个位置是随机的，所以只交换 count 次，而不是把整个池子洗一遍：

    源码节选 · KnowledgeBaseInterviewService.pickFollowUps
    if (pool == null || pool.size() < count) {
    throw new BusinessException(ErrorCode.INTERVIEW_QUESTION_INSUFFICIENT,
        "追问池在组装面试时发生变化，无法严格抽取 " + count + " 个追问");
}
if (count == pool.size()) return new ArrayList<>(pool);
List<KnowledgeBaseQuestionFollowUpDTO> copy = new ArrayList<>(pool);   // 复制一份，不动原列表
for (int i = 0; i < count; i += 1) {
    int j = random.nextInt(i, copy.size());      // 在 [i, size) 里随机选一个
    swap(copy, i, j);                            // 换到第 i 位
}
return copy.subList(0, count);
// 例：追问池 [A, B, C, D, E]，count = 2
//   i=0：从 0–4 里抽到 3 → [D, B, C, A, E]
//   i=1：从 1–4 里抽到 4 → [D, E, C, A, B] → 取前两个 [D, E]

    万一在“查容量”和“开始”之间题库被改了导致追问不够，直接报错而不是少问几个。组装好的题目列表交给文字面试的会话服务创建会话，来源标记为 KNOWLEDGE_BASE，之后答题、评估、报告全部复用文字面试的链路。

    这部分的边界是用测试逼出来的：54e1bb0 先写严格容量的测试，9cdcb8c 严格校验追问数量，0b99aaa 完善容量边界；完成面试后的跳转与结果展示也是 20ca85c 先复现、1f82388 再修复。

    实现细节与问题

    • 删不掉的知识库：题目表对知识库有外键但没有级联删除，知识库实体上也没有映射题目集合，删除服务只处理了问答会话的关联。一旦生成过题库，删除这个知识库就会因外键约束失败。这个场景没有测试覆盖。
    • 重新生成会清空整个题库：生成成功后在事务里先删除该知识库下的全部题目，再写入新题，包括用户已经启用、编辑过、甚至手动新增的题。生成弹窗只写着“生成草稿题”，没有任何覆盖提示。另外 Prompt 里传入“已有题目以避免重复”，而这些题马上就会被删掉，两个设计意图互相矛盾。更合理的是只替换草稿，或者追加。
    • 配置注入的方式：生成服务用 @Value 注入 Prompt 资源，并且每次调用都重新读文件，违反了项目“不要在 Service 里散落 @Value”的规则，其他服务都是通过配置属性类加载一次。
    • 题库面试不幂等：普通文字面试有请求 ID 防重复创建，题库面试的创建接口没有，连点两次会建两个会话。

    面试日程

    用户把飞书、腾讯会议、Zoom 的邀约文本粘进来，系统识别出公司、岗位、时间、会议链接和轮次，用户确认后保存到日历。日历基于 react-big-calendar，有月、周、日视图和列表视图，支持拖拽事件改期、拖动边缘调整时长。

    规则优先，模型兜底

    1. 按来源（没传就按文本里的关键词：“飞书”“腾讯会议”“会议号”“zoom.us”）选择对应的正则解析器，关键词都没有时三种依次尝试。
    2. 只有同时拿到公司、岗位、时间才算规则解析成功，返回置信度 0.95、来源 rule。
    3. 否则调用模型：Prompt 里带上当天日期（用来推算“明天下午两点”这类相对时间），默认时长 30 分钟，要求输出纯 JSON；代码再剥掉可能的 Markdown 代码块、容错解析时间格式。成功返回置信度 0.8、来源 ai。
    4. 都失败则提示解析失败，用户手动填写。

    这个设计的出发点是成本和确定性：格式规整的邀约用正则就够了，毫秒级、零成本、结果确定；只有规则搞不定的才花一次模型调用。另有一个每小时整点执行的定时任务，把时间已过、仍是“待面试”的日程批量改成“已取消”。

    实现细节与问题

    • 会议号重复：腾讯会议解析器取的是整个匹配而不是捕获组，结果会变成“会议号: 会议号：123456789”，密码同理。用一段邀约实际跑一遍腾讯会议的正则：
      走一遍：腾讯会议规则解析的输入与输出 
      输入：
  【面试邀请】
  公司：字节跳动 抖音电商
  岗位：后端开发工程师
  时间：2026-09-03 14:00
  腾讯会议 会议号：123456789 密码：8888

(?:会议号|ID)[：:]?\s*(\d{9,})  用 group() 取整个匹配 → meetingLink = "会议号: 会议号：123456789 密码: 密码：8888"
(?:公司|单位)[：:]\s*([^\s\n]{1,50})  取到第一个空白为止  → companyName = "字节跳动"（“抖音电商”丢了）
(\d{4}[-/]\d{2}[-/]\d{2})\s+(\d{2}:\d{2})                → interviewTime = 2026-09-03 14:00

而腾讯会议客户端复制出来的真实邀请写的是“#腾讯会议：123-456-789”，
会议号带短横线、前缀也不是“会议号”，这条正则根本匹配不到。
    • Zoom 规则永远不完整：Zoom 解析器只提取链接和时间，不提取公司和岗位，而“成功”要求三者齐全，所以 Zoom 邀约的规则解析形同虚设，必然走模型。事实上多数真实邀约没有“公司：”“岗位：”这样的标签，飞书和腾讯的规则也很难命中。
    • 来源被当成了模型 ID：模型兜底时把来源参数（feishu、tencent、zoom）当作 Provider ID 传进注册表，会因为找不到 Provider 而失败。前端目前不传来源，所以没有暴露，但接口本身是坏的。
    • 过期即取消的语义：面试时间过了不代表面试取消了，更可能是面试已经进行、用户没来得及标记。自动改成“待确认”会更贴近真实情况。
    • 置信度是常量：0.95 和 0.8 是写死的，并不反映这次解析的可靠程度。

    系统设置

    设置页管理模型 Provider：新增、编辑、删除、测试连通性，分别选择默认的聊天模型和默认的向量模型，以及语音识别与合成的参数。注册表本身的设计见 AI 底座 · 多模型注册表，这里讲设置功能的实现。

    • Key 加密存储：API Key 用 AES-GCM 加密后存库，每次加密生成 12 字节随机 nonce，认证标签 128 位，nonce 和密文分别 Base64 存储。主密钥来自环境变量：如果是 32 字节的 Base64 就直接用，否则对字符串做 SHA-256 得到密钥。没配置主密钥时默认拒绝启动，只有显式打开开发开关才会用内置的开发密钥。接口返回的永远是打码后的 Key。
      走一遍：保存一个 Key 之后库里存的是什么 
      APP_AI_CONFIG_ENCRYPTION_KEY=my-local-secret     → 不是 32 字节 Base64 → SHA-256 得到 32 字节 AES-256 密钥
明文 Key（35 字符）：sk-4f1c2e9a7b3d48e6a0c5f19d2b7e8a31
llm_provider_config.api_key_nonce      = 8gg+F7DBl0Iy6Ou5                     （12 字节随机数的 Base64）
llm_provider_config.api_key_ciphertext = X4qZ/adeZiVpq3+KFW9Q+SOSZ2VJ…         （35 字节密文 + 16 字节认证标签 = 51 字节）
设置页看到的 maskedApiKey              = sk-***a31                            （前 3 位 + *** + 后 3 位）

同一个 Key 再保存一次，nonce 不同，密文也完全不同；
改了 APP_AI_CONFIG_ENCRYPTION_KEY 之后，解密时 GCM 校验认证标签失败，
报“解密 Provider API Key 失败，请检查 APP_AI_CONFIG_ENCRYPTION_KEY”。
    • 连通性测试：用 Provider 的配置发一个最小请求（一句“Reply with OK only.”，max_tokens 为 1），先试 {baseUrl}/chat/completions，地址里没有版本号时再试 /v1/chat/completions；连接超时 5 秒、读超时 10 秒；失败时把状态码和截断后的响应体返回给页面，方便排查。
    • SSRF 防护：测试请求用的 HTTP 客户端挂了地址过滤器，只允许公网地址、回环地址和 198.18.0.0/15。放行回环是为了支持本机的 LM Studio，放行 198.18.0.0/15 是因为很多本地代理工具的 fake-ip 模式会把域名解析到这个网段。
    • 向量模型防呆：开启向量能力的 Provider 必须填向量模型名和维度，模型名如果像聊天模型（以 glm-、deepseek、qwen、kimi 等开头）会被拒绝，并提示该厂商推荐的向量模型名。这是踩过坑之后加的：把聊天模型填成向量模型，向量化会全部失败。
    • 并发与热加载：所有读操作拿读锁、写操作拿写锁，写完调用注册表的 reload 清空客户端缓存，下一次调用按新配置重建，不用重启。
    设置模块的保留意见

    地址过滤只加在“测试连通性”这一条路径上，保存 Provider 时并不校验 baseUrl，之后真正的模型调用也不经过过滤器，所以它挡住的只是“借测试接口探测内网”，而不是“把模型请求指向内网”；再加上所有管理接口都没有鉴权，这层防护意义有限。写操作是在 @Transactional 方法内部加锁、在 finally 里解锁，解锁发生在事务提交之前，其他线程可能在提交前读到旧数据；注册表的 reload 也在提交前执行。主密钥没有版本号，更换密钥会让库里所有 Key 无法解密，需要设计轮换方案。语音参数写进了 ~/.interview-guide 下的文件，但启动时并不读取，重启后丢失，见 架构 · 部署。
