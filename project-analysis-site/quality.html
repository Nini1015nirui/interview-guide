    项目解析 · 质量与问题

    测试、CI 与代码审查：这个项目的质量做到了哪一步

    这一页先讲项目怎么保证质量：测试怎么写、哪些是用“先复现再修复”的方式写出来的、CI 跑什么、提交规范怎么强制。然后是一份按严重程度排序的代码审查清单，共 18 条，每条都给出位置、影响和修复建议。面试官问“这个项目有什么不足”“如果让你继续做会怎么改”，答案就在这里；你真正动手修掉其中几条，就是简历上最有说服力的差异化内容。

    测试策略

    后端有 36 个测试类、约 8 千行，技术栈是 JUnit 5 + Mockito + AssertJ，测试意图用中文 @DisplayName 写，复杂场景用 @Nested 分组。绝大多数是不启动 Spring 容器的纯单元测试，依赖全部 mock，所以整套测试在 CI 上两分钟内跑完。

    区域测试类重点覆盖
    语音面试14会话服务（单个测试类 865 行）、评估恢复、上下文压缩、摘要持久化、WebSocket 处理器、ASR / TTS 服务（含握手失败回归）、评估接口
    知识库5向量化影子写入与清理（604 行）、题库异步生成与状态机（581 行）、容量与严格抽题
    文件处理4Tika 解析（含用真实样例文件的集成测试）、文本清洗、对象存储
    文字面试4幂等创建、评估适配、持久化、列表 DTO
    模型接入与设置5注册表、路径解析、Provider 增删改查与连通性测试、控制器
    限流3Lua 脚本、异常、Testcontainers 启动真实 Redis 7 的多维原子性集成测试
    其他1AppTest

    测试的分布和提交历史是吻合的：越是出过问题、被“复现再修复”过的模块，测试越厚。反过来，下面这些核心类没有任何直接的测试：结构化输出执行器、统一评估引擎、出题服务与 Skill 题量分配、RAG 查询服务、邀约解析、简历模块（上传、分析、删除）、知识库删除服务、Stream 消费者模板。审查清单里好几条问题恰好就落在这些没有测试的地方。项目也没有配置 JaCoCo，TDD 证据文档里都如实写了“无法给出数值覆盖率”。

    一个值得单独讲的发现

    全仓库唯一启动 Spring 容器的集成测试 VoiceInterviewIntegrationTest 被 @Disabled 了，理由写的是“测试配置里的 Provider 配置漂移导致 NPE”。实际上 application-test.yml 本身就不是合法的 YAML：提交 6b14836 把两处 model: qwen-plus 替换成 model: qwen3.5-flash 时丢了缩进，第 37 行起解析就会报错。禁用注解也是同一个提交加的。而名为 contextLoads 的 AppTest 只断言了 App.class 不为空，并不真正启动容器。结果是：CI 里没有任何测试验证过应用能完整启动、配置能正确绑定、Flyway 迁移能在真实数据库上执行。这个例子在 Claude Code 复刻 一页还会再讲一次。

    TDD 证据：先复现，再修复

    2026 年 7 月之后的大部分修复都遵循同一个节奏：先提交一个失败的测试（RED），再提交修复（GREEN），最后跑全量回归。仓库里留下了 6 份证据文档（.claude/tdd/ 下 4 份，docs/testing/ 下 2 份），格式统一：

    1. 来源与用户旅程：这次改动由什么驱动（用户反馈、现场日志、优化方案），用户视角下要保证什么。
    2. RED 记录：执行的精确命令、失败了几个用例、失败证据说明了什么，以及 RED 检查点的提交号。
    3. GREEN 记录：同样的命令转绿，加上全量回归、前端构建、必要时的浏览器验收或真实云服务烟测。
    4. 测试规格表：每一行是“保证了什么 → 哪个测试 → 测试类型 → 结果”。
    5. 覆盖率与已知缺口：没有覆盖率工具就明说，浏览器验收用了哪些临时数据、事后如何清理。

    这些文档本身就是很好的面试素材：它说明团队（很可能是在 AI 编码工具的辅助下）用“可执行的证据”而不是“我觉得修好了”来判断完成。TTS 那份文档里还有一个细节：验证时写了一个调用真实 DashScope 的临时烟测，确认通过后删除，既证明了修复在真实环境有效，又没有把依赖外部服务的测试留在套件里。

    CI 与提交规范

    • GitHub Actions（b2d1ca0）：推送到主分支或向它提 PR 时触发；同一分支的新提交会取消正在跑的旧任务；权限只给 contents: read。后端任务在 Temurin 25 上执行 ./gradlew :app:test，限流集成测试会通过 Testcontainers 拉起 Redis 容器；前端任务用 packageManager 字段里锁定的 pnpm 版本、Node 24 和 --frozen-lockfile 安装依赖，跑 4 个纯函数测试，再执行生产构建。
    • CI 没覆盖的：Playwright 端到端测试、另外 2 个纯函数测试、ESLint（配置文件存在但没有脚本调用）、覆盖率、Docker 镜像构建，以及前面说的“应用能否启动”。
    • 提交信息钩子：.githooks/commit-msg 要求标题是 feat|fix|refactor|perf|test|docs|chore|build|ci|revert 加可选作用域、冒号后必须含中文，标题和正文之间空一行，正文每一行都以 - 开头且含中文；Merge、Revert、fixup 等自动生成的信息放行。钩子本身还有一个测试脚本，覆盖 7 种应接受和 6 种应拒绝的写法。需要手动执行 git config core.hooksPath .githooks 才会生效。
    • 规则合规扫描：提交 5c878a3（“CLAUDE.md 合规性修复”）和 f87f435 按项目规则全仓扫描并修正了 @Value 散落、Executors 工厂方法、RuntimeException、事务内调用模型等问题。这类“用规则文件驱动的批量整改”是 AI 编码工具擅长的工作。

    代码审查清单（18 条）

    以下问题都在 commit b2d1ca0 的源码里核对过，按影响排序。“级别”的含义：P1 会导致错误结果、数据丢失或功能不可用；P2 安全、可靠性或在特定条件下出错；P3 性能与可维护性。

    编号位置问题与影响修复建议
    Q01 P1 KnowledgeBaseDeleteService、V1__init_schema.sql 题目表对知识库有外键但无级联，删除服务也不删题目。生成过题库的知识库无法删除，接口报错。没有测试覆盖。 在删除事务里先批量删除题目（或新增迁移加级联），补一个“有题目时删除成功”的测试。
    Q02 P1 QuestionGenerationStateService.replaceQuestionsAndComplete 重新生成会删除该知识库下全部题目，包括已启用、编辑过、手动新增的题；前端没有提示。Prompt 里“避开已有题目”与“全部替换”互相矛盾。 只替换 DRAFT 题，或提供“追加 / 替换草稿”选项；替换前前端二次确认。
    Q03 P1 ResumeGradingService.analyzeResume 模型失败时返回 0 分“错误报告”，消费者照常保存并标记完成。Stream 重试、FAILED 状态和“重新分析”入口全部失效，用户看到一份 0 分报告。 失败时抛出业务异常交给模板重试，重试耗尽标记 FAILED；删除 0 分兜底。
    Q04 P1 VoiceInterviewEvaluationService generateEvaluation 在同类里调用 @Transactional 的保存方法，事务不生效；保存总是插入新行，评估已落库但状态未更新时被恢复任务重投，会撞唯一约束而被标记失败。 把保存拆到独立 Service 或用 TransactionalExecutor；按会话 ID 查找后更新（upsert）。
    Q05 P1 InterviewController.createSession 请求体上写了题量 3–20、方向非空的校验注解，但参数前漏了 @Valid，约束不生效，出题服务也不截断题量，可以请求任意数量的题。 加 @Valid，Service 内再夹紧一次；补一个控制器校验测试。
    Q06 P1 InterviewController.getReport 遗留的 GET /report 会在请求线程里同步重跑整场评估并覆盖已有报告，没有限流。前端已不再调用，但它是一个能被反复触发的昂贵操作。 删除，或改成只读取已生成的报告。
    Q07 P1 VoiceInterviewWebSocketHandler.afterConnectionClosed、api/voiceInterview.ts 前端在非正常断开后自动重连最多 3 次，后端却在断开时立即结束会话并投递评估。网络抖动后用户在新连接里继续答题，评估已按不完整记录生成。 断开后给一个宽限期（如 60 秒）再结束；或前端重连前先调用恢复接口，后端拒绝已结束会话的连接。
    Q08 P1 DashscopeLlmService 语音记录与实际播报不一致：回复在合成之后才截断到 120 字，多出的句子被念出来却不在记录里；模型失败时“AI 服务暂时不可用”被当作面试官发言念出、落库并进入评估。 截断前置到句子分发环节；模型失败走 error 消息通道，不落库、不进上下文。
    Q09 P2 application-test.yml、VoiceInterviewIntegrationTest、AppTest 测试配置不是合法 YAML，唯一的容器级集成测试被禁用，contextLoads 不加载容器。CI 从未验证应用能启动、配置能绑定、迁移能执行。 修正缩进，启用集成测试；用 Testcontainers 的 PostgreSQL + pgvector 跑 Flyway 迁移和一个真正的启动测试。
    Q10 P2 全局、RateLimitAspect 没有任何鉴权，所有管理接口（含 Provider 与 Key 管理）对网络上的任何人开放；限流的 IP 维度直接信任 X-Forwarded-For，用户维度读 X-User-Id 请求头，都可伪造。 接入登录与鉴权（至少保护设置类接口）；只信任网关写入的来源头，用户 ID 从认证上下文取。
    Q11 P2 LlmProviderConfigService 地址过滤器只加在“测试连通性”上；保存 Provider 时不校验 baseUrl，真正的模型调用也不过滤，可以把模型请求指向内网地址。 保存时校验协议和解析后的地址，并在模型客户端的 HTTP 工厂上统一挂过滤器。
    Q12 P2 LlmProviderConfigService 写操作 在 @Transactional 方法内部加写锁、finally 里解锁，解锁早于事务提交；注册表 reload 也在提交前执行。如果在“清空缓存”和“提交”之间有请求到达，它会按数据库里仍是旧值的配置重建客户端并缓存下来，这次修改在下一次 reload 之前都不会生效。 由外层非事务方法先加锁再调用事务方法；在 afterCommit 回调里执行 reload。
    Q13 P2 LlmProviderBootstrapService.seedProvidersIfNecessary @PostConstruct 方法上的 @Transactional 不会生效（初始化回调时代理不参与），YAML 种子数据的多条写入不在同一个事务里，中途失败会留下一半的配置；多实例同时启动时可能同时判断“需要初始化”而发生主键冲突。 改为监听 ApplicationReadyEvent 调用事务方法，或用 TransactionTemplate；写入前加分布式锁或依赖唯一约束。
    Q14 P2 RagChatController、前端 stream.ts 流式问答只处理完成和出错，不处理取消：用户中途离开，助手占位消息永远停在“未完成”且内容为空；前端也没有停止生成的能力。 用 doFinally 按信号类型收尾，取消时保存已生成内容并标记中断；前端接入 AbortController。
    Q15 P2 VoiceInterviewPromptService 语音模式选择“JD 自定义方向”时，JD 原文只落库不进 Prompt，系统提示词变成“custom 方向的面试官”，还会让模型加载一个不存在的技能。 自定义方向时直接把 JD 与解析出的类目注入系统提示词，不走 Skill 工具。
    Q16 P2 voice-interview-context-summary.st 占位符写成 <previousSummary>、<newTurns>，与 Spring AI 默认的花括号分隔符不一致，开启摘要模式后模型收不到真实对话。单测 mock 了模型调用所以没发现。 改为 {previousSummary}、{newTurns}，补一个断言“渲染结果包含对话原文”的测试。
    Q17 P3 ResumeHistoryService.getAllResumes 每份简历额外查询最新分析和面试记录，N 份简历 2N+1 条 SQL，违反项目“不要循环调用 DB”的规则。语音会话列表统计消息数也有同样问题。 用一条聚合查询或两次批量查询后在内存里组装。
    Q18 P3 application.yml、.claude/rules/ 配置与文档漂移：短查询阈值代码默认 0.25、yml 默认 0.18（yml 生效，与 1bf8f1b 的意图相反）；语音的自动提交、限流、音频编码配置没有任何代码读取；规则文件仍写着 Provider 配置来自 yml、消费者实现 processMessage()，与现状不符。 默认值只保留一处；删除失效配置；规则文件随架构变更一起更新，并用启动校验或测试守住关键配置。

    更多小问题

    下面这些影响较小，或者在其他页面已经展开过，列在这里备查：

    • 日程解析：腾讯会议正则取整个匹配导致“会议号: 会议号：…”重复；Zoom 规则不提取公司和岗位，永远走模型；来源参数被当作 Provider ID（前端未传所以未暴露）；过期日程被改成“已取消”的语义不妥；置信度是常量。见 业务模块 · 日程。
    • RAG：拒答短语判断会误伤部分回答；向量表元数据没有索引；HNSW 加过滤的召回风险；分块无重叠、无混合检索与重排。见 业务模块 · RAG。
    • 异步模板：每条管线单线程消费；除题库生成外领取不是比较后更新；没有死信；大正文直接放进消息体。见 可靠性 · Stream 模板。
    • 语音：每轮可能多一次 Skill 工具往返；阶段化逻辑只在测试里被调用；每句合成新建一条连接；会话缓存直接缓存 JPA 实体。见 语音面试 · 已知问题。
    • 前端：两个 CDN 脚本阻塞所有页面首屏且 VAD 已空转；两份锁文件；onnxruntime 版本与 CDN 不一致；Dockerfile 与 CI 的 Node 版本和依赖锁定方式不同。见 前端 · 值得改进。
    • 接口约定：PDF 导出失败返回 HTTP 500 空响应，绕开了统一的 Result；多处把异常原文拼进返回给前端的提示；提交答案等接口用 Map 接参再强转；文字面试控制器直接调用持久化服务。
    • 简历：删除顺序与知识库相反（先删文件后删库）；并发上传同一文件会留下孤儿文件。
    • 代码规范：题库生成服务用 @Value 注入资源；报告保存方法里有内联的全限定类名；结构化输出默认用挂着工具的客户端；评估的类别分算出来了但前端没有展示；题目的 STALE 状态从未被使用。

    Agent 专项审查（12 条）

    上面 18 条是通用的后端与工程问题。面 Agent 岗时更有分量的是另一组与模型调用链路相关的问题，大部分都在与项目相同的 Spring AI 2.0.0 上用最小实验复现过，完整清单见 源码实验 · Agent 专项发现。其中四条影响最大：

    • A01 工具回合丢失用户消息：默认配方关闭了 ToolCallingAdvisor 的内部历史又没有记忆 Advisor，模型一旦调用工具，第二轮只剩系统消息和工具结果。
    • A02 关键词护栏误伤：候选人在回答里引用注入话术，整批评估按 0 分兜底；知识库资料里出现同样的短语，RAG 直接拒答。
    • A03 结构化重试放大：外层 2 次 × 校验 Advisor 1+3 次，最坏 8 次模型请求，指标只显示 2 次。
    • A04 摘要模板空转：即本页 Q16，已用真实模板渲染证实，开启压缩反而丢失早期对话。

    把清单变成你自己的贡献

    如果准备把这个项目写进简历，最有价值的做法是 fork 仓库，挑 3–5 条真正修掉，每条都按项目自己的 TDD 节奏留下证据。推荐的顺序和理由：

    1. 先修 Q09（测试配置与容器级测试）：它是其他修复的地基。修好 YAML、启用集成测试，再用 Testcontainers 起一个带 pgvector 的 PostgreSQL 跑 Flyway，你就有了“应用能启动、迁移能执行”的保障。面试时可以讲“我发现 CI 绿但从没验证过启动”。
    2. 再修 Q01 + Q02（题库删除与覆盖）：两条都是数据问题，复现简单（有题目时删除、重新生成后启用题消失），修复范围小，前后端都涉及。
    3. 然后是 Q03 或 Q04（异步任务的失败语义）：能展示你对“降级不能吞掉失败信号”“同类自调用让事务失效”的理解，这是面试官很爱追问的点。
    4. 如果面 AI 应用岗，加做 Q08 或 Q14：一个是语音链路的数据一致性，一个是流式输出的取消语义，都能引出对实时 AI 交互的深入讨论。
    5. 如果面 Agent 岗，优先做 A01–A04：project-analysis-site/lab 里已经有复现这四个问题的实验，把它们改写成项目里的 JUnit 测试就是现成的 RED，修复本身都很小，做法见 改造方案 · 修地基。

    每一条修复都按“失败测试 → 修复 → 全量回归”提交，PR 描述里写清楚复现步骤和验证方式。怎么把这些写成简历条目、怎么在面试里讲，见 简历与讲述。
