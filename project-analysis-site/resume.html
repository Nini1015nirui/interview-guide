    面试准备 · 简历与讲述

    简历写法与讲述脚本：把项目讲成你的项目

    这一页解决三个问题：简历上怎么写、面试时怎么讲（1 分钟、3 分钟、10 分钟三个版本和 5 个 STAR 故事）、被质疑时怎么接。所有内容都建立在一个前提上：讲你真正理解和做过的部分。

    先说原则：诚实与差异化

    InterviewGuide 的 README 明确写着欢迎拿它做个人项目经历或毕设，这意味着同一个项目会出现在很多人的简历上，面试官见过的概率不低。在这种情况下，“照搬 README 的功能列表”是最差的写法：既没有区分度，又经不起追问。三条原则：

    1. 角色如实：说清楚这是基于开源项目的学习与改进，还是从零实现。面试官问“这是开源项目吗”时能坦然回答，比被当场识破好得多。
    2. 只讲吃透的部分：宁可深讲两个模块，也不要浅讲七个。本站每个模块都标了源码位置和提交号，讲之前自己在代码里走一遍。
    3. 用改动建立差异：代码审查清单 里的问题都是真实存在的。fork 仓库，挑几条按“失败测试 → 修复 → 回归”修掉并留下提交记录，这些才是完全属于你的内容，也是面试官最愿意追问的部分。
    两条红线

    不要把原作者和社区贡献者的设计说成是自己独立完成的，也不要编造没有测过的数据（QPS、并发数、时延提升百分比）。如果你把修改后的版本部署成对外服务，注意项目采用 AGPL-3.0 协议，需要公开修改后的源码。

    先确定你的角色

    你的实际情况简历上的定位讲述重点
    通读源码、本地跑通、做过实验“基于开源项目 InterviewGuide 的学习与二次开发”对关键设计的理解和取舍判断，以及你做过的实验（比如调检索阈值、压测）
    在 fork 上修复了若干问题、补了测试“参与 / 主导若干模块的改进”你发现问题的过程、复现测试、修复方案和验证数据
    在它的基础上加了新功能“在开源项目基础上扩展 X 功能”新功能的设计，如何复用已有的异步模板、评估引擎等底座
    参考它从零实现了自己的版本“独立设计实现的 AI 面试平台”你的实现和原项目的差异，你做了哪些不同的选择、为什么

    简历条目写法

    写法遵循“动作 + 技术手段 + 解决的问题 + 结果”。下面三组示例按岗位方向组织，括号里的内容必须换成你自己的真实情况，数字要么来自你亲自测量，要么不写。

    Java 后端方向

    项目经历示例（后端）
    AI 智能面试平台（基于开源项目 InterviewGuide 二次开发）｜Spring Boot 4 · Java 25 · Spring AI 2.0 · PostgreSQL/pgvector · Redis · React
- 基于 Redis Stream 消费者组实现简历分析、向量化、面试评估、题库生成等 5 条异步管线，模板方法统一领取、重试（最多 3 次）、pending 回收（XAUTOCLAIM）与失败状态回写，配合事务提交后投递避免“消息早于数据”。
- 设计题库生成任务状态机：以 taskId 作为围栏令牌，在行锁内比较并迁移状态，旧任务结果自动丢弃；模型调用置于事务外，题目替换与完成状态在同一短事务内提交，并有定时任务恢复超时任务。
- 通过 URL 幂等键 + Redisson 分布式锁 + Redis 结果映射 + 数据库唯一索引四层保障，解决页面刷新导致重复出题的问题。
- 基于 Lua 脚本实现多维度（全局 / IP / 用户）原子限流：先只读校验全部维度、全部通过再统一扣减，使用 Testcontainers 验证多维回滚。
- （你的改进，按实际填写）修复知识库删除因外键约束失败、重新生成覆盖已启用题目等问题，补充复现测试；修复测试配置并恢复容器级集成测试，使 CI 覆盖应用启动与 Flyway 迁移。

    AI 应用开发方向

    项目经历示例（AI 应用）
    AI 模拟面试与知识库问答平台｜Spring AI 2.0 · OpenAI 兼容多模型 · pgvector · Qwen3 实时 ASR/TTS
- 设计多模型注册表：Provider 配置入库并以 AES-GCM 加密 API Key，按“默认 / 无工具 / 语音”三种配方缓存 ChatClient，支持设置页热切换聊天与向量模型。
- 封装统一的结构化输出执行器：JSON Schema 校验 + 携带上次错误原因的修复型重试 + 本地引号修复，替代各业务分散的解析逻辑；评估按 8 题分批、二次汇总，批次失败局部降级。
- 实现 Skill 驱动出题：按 ALWAYS_ONE / CORE / NORMAL 三阶段分配题量，按需注入参考题库，简历题与方向题 6:4 并行生成互为降级，用 10 字主题摘要做历史去重，控制上下文约 600 token。
- RAG 问答支持多轮查询改写、按问题长度自适应 topK 与相似度阈值、无命中不调用模型、流式输出前 120 字拒答探测；向量化采用影子写入 + 事务内提升，失败不污染线上检索。
- 实时语音面试：AudioWorklet 采集 16k PCM，LLM 流式输出按句切分并发合成（并发上限 3）、按序号有序下发，四层回声防护；定位并修复识别重连回调误删新连接、TTS 握手阻塞等问题。

    Agent 应用开发方向

    项目经历示例（Agent 岗）
    AI 面试训练平台 · Agent 化分析与改进（基于开源项目 InterviewGuide）｜Spring AI 2.0 · Tool Calling · Agent Skills · pgvector · Qwen3 实时语音
- 梳理平台 12 个大模型调用点，按提示链、路由、分段并行、评估者-优化者等模式归类，定位出唯一的工具调用循环（语音面试），以及“默认配方给 7 个工作流步骤挂载工具”的结构性隐患。
- 基于 Spring AI 2.0 源码和自建的假模型实验工程，复现工具回合的消息序列，定位项目“多厂商工具调用不兼容”问题的根因为 ToolCallingAdvisor 历史开关配置（第二轮仅发送 SYSTEM 与 TOOL 消息），给出配置级修复与回归用例。
- 量化 Agent Skills 渐进式披露的成本（工具定义约 895 token，大于任一技能正文），据此把实时语音链路改为人设直接注入、参考资料由代码预取。（按实际完成情况填写）
- 复现并修复结构化输出重试放大（最坏 8 次模型请求）和关键词护栏误伤（引用注入话术的回答整批 0 分），改为带总预算的单层修复型重试与输出侧护栏。（按实际完成情况填写）
- 设计追问决策 Agent：两个只读工具加一个幂等写工具、结构化决策输出、工具预算与循环内侧硬上限，证据沉淀进评估报告；用金标集衡量评委与人工评分的一致性（MAE、Spearman）。（按实际完成情况填写）

    前两条只要你亲手读过源码、跑过 实验工程 就可以写；标了“按实际完成情况填写”的三条，必须在自己的 fork 上真正实现、并能展示提交和测试之后再写。

    讲述脚本

    1 分钟版本（自我介绍里带过）

    1 分钟

    我最近深入做的一个项目是 AI 面试训练平台，基于 Spring Boot 4 和 Spring AI，能做简历分析、文字和语音模拟面试，以及基于知识库的问答和出题。我主要关注的是怎么把大模型这种慢、贵、不稳定的调用做成可靠的产品：耗时任务用 Redis Stream 异步化并配了重试和恢复，结构化输出统一做修复型重试，题库生成用 taskId 做围栏防止旧任务覆盖新结果。在这个基础上我（按实际填写：修复了哪些问题 / 加了什么功能），比如……。如果您感兴趣，我可以展开讲其中任何一块。

    3 分钟版本（“介绍一下你的项目”）

    1. 背景与定位（20 秒）：做什么、给谁用、为什么要用大模型做。
    2. 架构一句话（20 秒）：模块化单体，PostgreSQL 加 pgvector 同时做业务库和向量库，Redis 做缓存、锁、队列和限流；请求分同步、异步、流式三类。
    3. 难点一（50 秒）：异步可靠性。Stream 模板怎么领取、重试、回收；为什么事务提交后才投递；题库状态机的 taskId 围栏。
    4. 难点二（50 秒）：按岗位选。后端岗讲幂等和限流原子性；AI 岗讲结构化输出和 RAG 检索策略；全栈或音视频相关讲语音链路。
    5. 你的贡献与结果（30 秒）：你修了什么、怎么验证的、效果如何。
    6. 收尾（10 秒）：“这个项目让我对 LLM 应用的工程化有了比较完整的认识，也清楚它还有哪些不足，比如……”

    10 分钟版本（专门的项目深挖环节）

    结构和 3 分钟版一样，但每个难点都按“问题 → 方案 → 取舍 → 验证”展开，并主动画图。建议提前练熟这四张图，面试时在白板或共享屏幕上边画边讲：

    • 三种交互方式（总览）
    • Stream 消费者循环（可靠性）
    • 题库状态机（可靠性）或向量影子写入（业务模块）
    • 语音一轮对话的时序（语音面试）

    10 分钟版本里一定要留出“不足与改进”的一段，主动讲两三条审查发现和你的处理，这会把谈话引向你最有准备的领域。

    五个 STAR 故事

    故事一：旧任务覆盖新结果

    情境
    知识库题库生成是异步任务，用户可以反复点“生成”。测试发现两个问题：首次消费失败后状态一直停在“生成中”；用户重新提交后，上一次还在跑的任务把旧结果写了进来。
    任务
    保证同一知识库任意时刻只有一个有效任务，旧任务的结果不能生效，失败能恢复，且不能在事务里调用模型。
    行动
    先写复现测试，13 个用例里 2 个按预期失败。然后引入 taskId 作为围栏令牌：每次提交生成新 ID，所有状态迁移都在行锁内比较 ID 和预期状态；模型调用在事务外，最后一个短事务再次核对后替换题目并标记完成；再加恢复调度处理超时任务，生成参数存快照。
    结果
    复现测试全部转绿，全量回归、前端构建、PostgreSQL 迁移和浏览器主流程都通过；前端只在同一任务完成时刷新列表，消除了“暂无题目”的假象。

    故事二：第三轮起没有声音

    情境
    语音面试前两轮正常，从第三轮开始识别不再返回结果，偶发、难复现。
    任务
    找到根因并保证识别连接断开后能可靠恢复。
    行动
    通过日志发现云端识别连接会被服务端关闭，代码在发送失败时会重建连接。进一步发现旧连接的关闭回调是异步触发的，可能晚于新连接建立，而它按会话 ID 删除会话表里的记录，把新连接一起删了。修复为关闭回调只删除“对象身份与自己相同”的连接，并为同一会话的启停加锁；发送失败时自动重连并重发当前音频帧。
    结果
    问题不再出现。这个问题的本质是“异步回调按 key 修改共享状态时没有确认状态是否已被替换”，和乐观锁、CAS 要解决的是同一类问题。

    故事三：重新向量化失败导致知识库残缺

    情境
    早期重新向量化是“先删旧向量，再逐批写新向量”，中途某批 Embedding 调用失败，知识库就只剩一部分向量，问答质量骤降。
    任务
    让重新向量化要么完整成功、要么完全不影响现有数据，且过程中问答不中断。
    行动
    改为影子写入：新向量带临时知识库 ID 写入，对检索不可见；全部成功后在一个事务里删除旧向量并用 jsonb_set 把临时 ID 提升为正式 ID；失败时按任务 ID 清理临时数据。几十次 Embedding 调用都在事务外，事务里只有两条 SQL。
    结果
    失败不再污染线上检索，切换在一次提交内完成，并发的两个任务也不会新旧混杂。这个方案能成立的前提是业务库和向量库是同一个 PostgreSQL，这也是当初选 pgvector 的理由之一。

    故事四：你自己的修复（模板）

    这是最重要的一个故事，用你在 fork 上真实完成的修复来写。以“知识库删不掉”为例：

    情境
    阅读源码时发现题目表对知识库的外键没有级联，而删除服务不删除题目，推断“生成过题库的知识库无法删除”。
    任务
    先证实，再以最小改动修复，并防止回归。
    行动
    写一个集成测试：创建知识库和题目后调用删除，测试按预期因外键约束失败。修复为在删除事务里先批量删除题目（或新增迁移加级联），测试转绿，再跑全量回归。
    结果
    （按实际填写）提交记录、测试名称、PR 链接。面试时可以顺带讲：为什么选择在服务层删除而不是数据库级联（可见性、审计、与向量和文件的清理顺序一致）。

    故事五：工具调用真的“不兼容”吗（Agent 岗）

    情境
    项目在 4 月让出题通过 Skill 工具加载人设，10 天后退回“后端直接注入”，提交说明把原因归结为“不同厂商对工具调用消息链路的校验不一致”；而默认配方今天仍然给 7 个调用点挂着这个工具。
    任务
    判断这个结论是否成立：工具调用是真的不可用，还是项目自己的问题。
    行动
    读 Spring AI 2.0 的 ToolCallingAdvisor 源码，注意到关闭内部历史后下一轮只发“系统消息 + 最后一条消息”；写一个第一轮请求工具的假模型，按项目配置复刻 Advisor 组合，打印每一轮发给模型的消息；再下载当时使用的 2.0.0-M4 源码核对同一段逻辑，并把相关提交按时间排好。
    结果
    第二轮请求只剩 SYSTEM 和 TOOL，用户消息和 tool_calls 都被丢掉，严格校验的接口会直接拒绝，这比“厂商不兼容”更能解释当时的现象。修复只需删掉手动注册的 Advisor、把默认配方的工具去掉；实验保留下来，作为以后升级框架时的回归用例。详细证据见 根因复盘。

    被质疑时怎么接

    “这不是 GitHub 上那个开源项目吗？”

    坦然承认，然后把话题引到你的理解和改动上：“是的，我是基于这个开源项目做的学习和二次开发。我读完了全部源码和提交记录，重点研究了异步任务和 RAG 两块，并且在自己的 fork 上修复了几个问题，比如……我可以讲讲其中一个是怎么发现和验证的。”

    “这么多功能，都是你一个人做的？”

    不要硬扛。“不是，整体框架来自开源项目，我负责 / 深入的是 A 和 B 两块。A 这块的难点是……”然后马上进入细节。面试官要判断的是你的深度，而不是项目的广度。

    “是不是用 AI 写的？”

    如实说用了哪些 AI 工具、怎么用的，并强调你负责的部分：定义问题和验收标准、设计关键方案、审查 AI 的改动、用测试证明结果。可以举仓库里的反例说明你知道 AI 会出什么错，比如它改坏了测试配置又把失败的测试禁用掉。详见 Claude Code 复刻 · 怎么谈 AI 辅助开发。

    “你说的这个优化，有数据吗？”

    有就讲怎么测的（环境、方法、样本量）；没有就直说“这是设计层面的推理，我没有做过压测”，再讲你会怎么测。编造的数据一追问就露馅。

    “为什么不用 X（Kafka、Milvus、LangChain4j……）？”

    先讲当前选择在当前规模下的理由，再讲什么条件下会换成 X。例如：“Stream 在任务量小、已有 Redis 的前提下足够；需要回放、多个下游订阅或者堆积量很大时，我会换 Kafka。”这样回答既不否定对方，也体现了判断力。

    让这个项目真正属于你

    • 修问题：从 修复顺序建议 里挑 3–5 条，每条一个 PR，带复现测试和验证说明。
    • 补评测：为出题、评估或 RAG 建一个小评测集，改一次 Prompt 或阈值就跑一次，把结果做成表格。这在 AI 应用岗面试里非常加分。
    • 跑实验：在 project-analysis-site/lab 里复现 A01–A05，再把实验改写成项目里的测试并修掉，这是 Agent 岗最有说服力的差异化，路线见 改造方案 · 修地基。
    • 补指标：给语音链路加“首句音频到达浏览器”的时延，给模型调用加 token 和费用统计，截图放进你的博客。
    • 部署上线：修好 WebSocket 地址和 Nginx 配置，加上登录，部署到云服务器，面试时可以现场演示。
    • 写出来：把一两个故事写成技术博客，本站的结构可以直接借用。

    面试前一晚的检查清单

    1. 能在 1 分钟和 3 分钟内讲完项目，不看稿。
    2. 能不看资料画出四张图：三种交互、消费者循环、状态机、语音时序。
    3. 准备好 2 个 STAR 故事，其中 1 个是你自己的修复。
    4. 把 问答页 前 20 题用自测模式过一遍。
    5. 准备好“项目的三个不足”和“如果重做会怎么改”。
    6. 打开自己的 fork，确认能随时展示提交记录和测试。
