    项目解析 · 前端

    前端工程实现：把异步和流式体验做顺

    前端是一个 React 18 + TypeScript 的单页应用，页面本身并不复杂，工程上值得讲的是它怎么配合后端的三种交互方式：统一的请求层消化“HTTP 200 + 业务码”，自己实现的 SSE 客户端读流式回答，一组轮询约定跟踪异步任务，以及语音面试的音频采集和播放。最后讲它的测试方式和构建部署。

    技术栈与结构

    框架
    React 18.3（StrictMode）· TypeScript 5.6（strict，未使用的变量和参数直接报错）· React Router 7
    构建
    Vite 5：开发时把 /api 代理到 8080；生产构建把 React、UI 库、代码高亮拆成三个独立的 vendor 包；另挂了 WASM 和顶层 await 插件，服务于语音的 ONNX 运行时
    样式与动效
    Tailwind CSS 4（含 typography 插件渲染 Markdown）· framer-motion · lucide-react 图标 · 明暗主题（本地记忆 + 跟随系统）
    功能库
    react-markdown + remark-gfm + react-syntax-highlighter（问答回答）· react-virtuoso（长对话虚拟列表）· Recharts（简历雷达图、面试得分趋势）· react-big-calendar（日程，支持拖拽改期）· dayjs
    目录约定
    api/ 每个后端模块一个文件，统一复用 request.ts；types/ 放共享类型；pages/ 放页面和它们的纯函数模块；components/ 放可复用组件；constants/routes.ts 放路由常量
    规模
    85 个 TS/TSX 文件约 1.8 万行，最大的几个页面是设置页（约 1500 行）、语音面试页（约 950 行）、面试记录页（约 890 行）

    所有页面都用 lazy 按需加载，外层一个 Suspense，布局组件提供侧边导航，分三组：面试准备（简历管理、模拟面试、面试记录、面试日程）、知识库（知识库管理、知识库面试、问答助手）、系统（设置），页面通过 Outlet 渲染。首页直接跳到简历管理。

    API 层：统一消化业务码

    后端约定所有接口都返回 HTTP 200，成败看 Result 里的 code。前端在一个 Axios 实例的响应拦截器里把这件事一次做完，页面代码拿到的永远是 data 本身，出错时拿到的是一个带后端原文提示的 Error：

    情况拦截器怎么处理页面拿到什么
    响应是 Result 且 code 为 200把 response.data 换成 result.data业务数据
    响应是 Result 但 code 不是 200reject 一个 Error，消息用后端的 message“简历不存在”这类可直接展示的提示
    HTTP 非 2xx 但响应体是 Result尝试解析响应体（包括 Blob）后端的 message
    没有响应，且是上传请求不假设是文件太大“上传失败，可能是网络超时或连接中断”
    没有响应的其他请求—“网络连接失败，请检查网络”
    • 文件下载：下载请求用 responseType: 'blob' 并跳过 Result 转换。难点在于：后端出错时返回的是 JSON 形式的 Result，但因为请求声明了 blob，它也会被包成一个 Blob。封装会检查 Blob 的类型和大小（JSON、文本或不超过 64KB 才尝试解析），能解析出 Result 就按错误处理，否则才当文件保存。
    • 超时分级：普通请求 60 秒；上传 300 秒，和 Nginx 的读超时对齐；创建面试、提交答案、非流式知识库问答这类可能等待模型的请求单独放宽到 180 秒。
    • 类型：request.get<T> 等方法直接返回 Promise<T>，每个模块的 API 文件定义自己的请求和响应类型。

    SSE 客户端：为什么不用 EventSource

    浏览器自带的 EventSource 只能发 GET 请求，不能带请求体，而问答接口需要 POST 一个 JSON。所以项目用 fetch 拿到响应流，再用 ReadableStream 的 reader 逐块读取、TextDecoder 以流模式解码，自己按 SSE 协议切分。这个客户端有几处考究：

    • 先判断是不是真的流：如果响应头是 JSON，说明后端在进入流式之前就报错了（比如限流、参数错误），这时按 Result 解析并抛出业务错误，而不是把一段 JSON 当回答显示出来。
    • 两种解析模式：“行模式”每遇到一行 data: 就回调一次；“事件模式”按空行切分事件块，同一块里的多行 data 按配置的连接符拼起来，并识别 event: error。两个流式接口的编码方式不同，所以分别使用不同模式。
    • 换行转义：SSE 用换行分隔事件，回答内容里的换行会破坏格式。后端推送前把 \n、\r 转义成字面量，前端再还原，Markdown 的段落和列表才能保持。
    • 流中的业务错误：某一条 data 如果是 JSON 且带有 error / failed 标记，同样按错误抛出。
    • 渲染节流：每来一个分片不直接 setState，而是把内容累加到变量里，用 requestAnimationFrame 合并到下一帧，并包在 startTransition 里降低优先级。一帧最多重渲染一次 Markdown，输入框不会卡。

    缺的一块是取消：整个前端没有使用 AbortController，用户不能中途停止生成，切走页面后请求也仍在后台读完。结合后端没有处理“取消”信号的问题（见 业务模块 · RAG），停止生成需要前后端一起补。

    路由与幂等创建

    文字面试的“刷新不重复出题”，前端这一半完全靠路由完成：

    1. 从任何入口进入 /interview，包装组件发现 URL 里没有请求 ID，就立刻用 crypto.randomUUID() 生成一个，replace 跳到 /interview/create/{uuid}，面试配置放在路由 state 里。
    2. 答题页挂载时用一个 useRef 标记保证只发起一次创建。React 18 的 StrictMode 在开发环境会把 effect 执行两次，没有这个标记就会创建两场面试（5c878a3 修复）。
    3. 创建请求带上这个请求 ID。等待期间用户刷新，URL 不变，请求 ID 不变，后端据此返回同一个会话。
    4. 创建成功后再 replace 到 /interview/session/{sessionId}。从此刷新走“恢复会话”：拉取会话，定位到当前题，恢复已填写的答案。两次 replace 保证浏览器历史里不会残留“创建”那一步，后退也不会重新触发创建。

    其他路由大多是字面量写在组件里，只有面试相关的几条放进了路由常量文件，这条项目规则只执行了一部分。

    轮询约定

    所有异步任务（简历分析、向量化、面试评估、题库生成、语音评估）的结果都靠轮询状态字段拿到，间隔统一是 3 秒（题库面试入口页是 5 秒）。代码里有两种写法，适用场景不同：

    setTimeout 链

    上一次请求返回后才安排下一次，请求不会堆积；组件卸载时设置取消标记。用在单个任务的详情页：语音评估页、题库生成页、题库面试的评估等待。

    条件 setInterval

    只有列表里存在“处理中”的条目才启动定时器，全部完成就停；刷新结果先做浅比较，没有变化就不 setState，避免整表重渲染。用在简历库和面试记录这类列表页。

    状态到界面文案的映射都抽成了纯函数。例如题库生成页只在“同一个任务从活动态变成 COMPLETED”时才刷新题目列表，防止首次加载时读到历史的完成状态而误触发刷新（20ca85c、1f82388）；语音评估在 PENDING 超过 2 分钟后把提示从“排队中”换成“等待较长，可以重新生成”。

    音频采集与播放

    采集

    1. 申请麦克风时打开浏览器的回声消除、降噪和自动增益。
    2. 建一个采样率 16kHz 的 AudioContext，加载 public/audio-worklet/pcm-processor.js。Worklet 在音频线程里运行：线性插值重采样到 16kHz，浮点转 16 位整数，攒够 3200 个采样（200 毫秒）通过 postMessage 交给主线程。
    3. 主线程把 ArrayBuffer 分块转成 Base64（每块 32KB，避免 String.fromCharCode 参数过多导致栈溢出），交给页面判断是否发送。
    4. 处理链末端接一个增益为 0 的节点再连到输出，保证处理链持续运转，又不会把麦克风声音从扬声器放出来。
    5. 另有一个分析节点每 100 毫秒计算一次平均音量，驱动界面上的音量动画。

    相比已废弃的 ScriptProcessorNode，AudioWorklet 不占主线程，页面渲染再忙也不会丢音频帧。

    播放

    • 分块模式（默认）：收到 audio_chunk 后跳过 44 字节 WAV 头，把 16 位整数转成浮点，写进一个 24kHz 的 AudioBuffer 推入队列；上一段的 onended 触发下一段，实现无缝拼接。收到最后一块或 audio_complete 后，每 100 毫秒检查一次队列是否播完（最多等 30 秒），播完才把 AI 这轮的文字定稿为消息气泡，并解除录音锁定。
    • 整段模式：收到完整 WAV 交给 <audio> 元素播放，同时从 WAV 头里读出字节率和数据长度估算时长，设置一个“时长 + 1.5 秒，限制在 4–60 秒之间”的看门狗，防止 ended 事件丢失导致界面一直显示“面试官正在回答”。
    • 自动播放限制：浏览器拒绝播放时提示“请点击页面任意位置以启用音频播放”，并直接结束本轮播放状态。

    页面状态机

    语音页用四个状态决定按钮能不能点：连接状态、识别是否就绪、AI 是否在说话、是否正在提交。“能录音”要求已连接、识别就绪、AI 没在说话、没有在提交；“能提交”要求有文本、AI 没在说话、没有在提交、已连接。这些状态同时存进 ref，因为 WebSocket 回调是在创建时捕获的闭包，读 state 会拿到旧值。为了防止某个信号丢失导致界面卡住，还有几个兜底计时器：只有文字没有音频时 2.5 秒后定稿，收到最终文字 15 秒后仍没有音频也定稿。

    测试

    纯函数单测：不引入测试框架

    前端没有引入 Jest 或 Vitest，而是把容易出错的判断逻辑从组件里抽成纯函数模块，用 Node 自带的测试运行器执行 node --test xxx.test.ts。Node 24 可以直接运行 TypeScript（类型擦除），不需要编译步骤，也不需要额外依赖。

    模块测什么CI 是否运行
    interviewEntry带会话 ID 时恢复、否则创建是
    interviewHistoryStats面试记录页的统计口径：普通页按全部记录统计，知识库页按筛选结果统计，评估中的不算已完成是
    questionGenerationStatus生成状态文案、何时刷新题目列表是
    interviewCapacity容量矩阵到可选项、提示文案的换算是
    voiceEvaluationStatus语音评估状态展示、2 分钟延迟边界否
    knowledgeBaseInterviewCompletion题库面试交卷后：评估中停在等待页，完成后进详情，失败时展示失败状态否

    后两个测试文件存在，但没有写进 package.json 的脚本，CI 也就不会运行它们。

    Playwright 端到端测试

    语音面试有 3 个浏览器端到端用例：麦克风音频发出后显示字幕和 AI 追问；提交后迟到的上一轮字幕不污染下一轮；结束面试后回到记录页。它们不依赖后端和任何云服务：

    • 用 Chrome 的假媒体设备参数提供虚拟麦克风，并预先授予麦克风权限；
    • 拦截 jsdelivr CDN 请求，用初始化脚本注入假的 VAD 对象；
    • 用初始化脚本把 window.WebSocket 替换成一个假实现：收到音频就回推一条字幕，收到提交就回推 AI 的追问，还暴露一个测试钩子，让用例能在任意时刻“从服务端”推送消息；
    • REST 接口用 page.route 返回固定的 Result。

    这套写法把一个依赖三个云服务的实时功能变成了可重复、秒级完成的测试，是 AI 编码时“先写复现用例再修”的直接产物（524d5ef、e9fc13f）。不过 CI 目前只跑纯函数测试和构建，端到端测试需要本地手动执行。

    构建与部署

    • 镜像：两阶段构建，第一阶段在 Node 镜像里安装依赖并执行 tsc && vite build，第二阶段只把产物复制进 Nginx 镜像。
    • Nginx：所有路径回退到 index.html，解决单页应用刷新 404；/api/ 反代到后端，读、写、连接超时都是 300 秒；上传上限 50MB，与知识库上限一致；开启 gzip。
    • 环境变量：VITE_API_BASE_URL 控制接口前缀（默认同源），开发时 VITE_API_PROXY_TARGET 控制代理目标。

    值得改进的地方

    • 首屏被 CDN 脚本阻塞：ONNX 运行时和 VAD 两个脚本写在 index.html 的 head 里同步加载，所有页面都要等它们下载完，而 VAD 在语音页里已经不参与任何逻辑。应该删除，或至少改成语音页按需加载。
    • 依赖版本不一致：package.json 里声明了 onnxruntime-web 1.24.3，页面实际从 CDN 加载的是 1.22.0；仓库里同时存在 package-lock.json 和 pnpm-lock.yaml 两份锁文件。
    • 构建环境不一致：CI 用 Node 24、固定的 pnpm 版本和 --frozen-lockfile；Dockerfile 用 Node 20、全局安装最新 pnpm、不锁依赖，镜像构建结果可能和 CI 验证的不同。
    • 测试没有全部进 CI：6 个纯函数测试只跑 4 个，端到端测试不跑。
    • 没有取消能力：流式回答不能停止，语音连接的自动重连和后端“断线即结束”的策略冲突，见 语音面试 · 已知问题。
    • 大组件：设置页约 1500 行，语音页把连接、音频、状态机、界面放在一个组件里，可以拆成自定义 Hook（例如 useVoiceSocket、useChunkedPlayer）后再做单测。
    • 交互细节：语音暂停用浏览器确认框的“确定 / 取消”表示两种暂停方式，容易误操作。
