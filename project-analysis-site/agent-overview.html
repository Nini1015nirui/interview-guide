    Agent 专题 · 总览

    用 Agent 的尺子量这个项目：哪里是工作流，哪里是 Agent

    面 Agent 应用开发岗，面试官最先想确认的不是你做了多少功能，而是你能不能准确说出“这个系统里，下一步做什么由谁决定”。这一页把项目里全部 12 个聊天模型调用点逐一列出，按工作流和 Agent 的经典模式归类，再用项目自带的《AI Agent 开发面试参考》里的 Harness 六层模型逐层审计，最后给出面试时的定性说法。后面几页分别深入机制、实验、改造方案和题库。

    源码基线：commit b2d1ca0 结论均标注源码位置或实验编号 精读约 25 分钟

    先给结论

    这是一个以确定性工作流为骨架的大模型应用，不是自主 Agent。12 个聊天模型调用点里，有 11 个的执行路径由后端代码写死：什么时候调模型、带什么上下文、要什么结构的输出、失败后怎么办，都由代码决定，模型只负责在一个“格子”里填内容。唯一真正的 Agent 循环在实时语音面试：模型在对话中可以自行决定调用 Skill 工具加载面试官人设，工具循环由 Spring AI 的 ToolCallingAdvisor 驱动。

    这个判断不是贬义。面试训练产品要求结果可复现、可评分、成本可控，工作流是正确的默认选择；项目历史上也恰好走过一次“先上工具调用、再退回确定性注入”的弯路，而那次“退回”的真正原因并不是厂商不兼容（见 源码实验 · 根因复盘）。面 Agent 岗时真正加分的，是讲清楚三件事：

    1. 哪些地方刻意不用 Agent，为什么：结果要被打分和复用、时延和成本有预算、失败要能逐步重试。
    2. 现有的那个工具循环有什么问题，你怎么验证的：本专题用 8 个最小实验在与项目相同的框架版本上复现了框架的真实行为。
    3. 如果要升级成真正的面试官 Agent，你怎么设计：循环、工具、终止条件、记忆、评估和护栏，每一项都给出可编译的代码草图。
    30 秒版本（Agent 岗）

    这是一个基于 Spring AI 2.0 的 AI 面试训练平台。从 Agent 的角度看，它的主体是工作流：简历分析、出题、评估、RAG 问答都由后端编排，模型输出统一走 JSON Schema 校验和修复型重试，耗时步骤放进 Redis Stream 做持久化执行；只有语音面试是一个带工具调用循环的对话 Agent。我重点研究了它的工具调用链路，用最小实验复现出：项目把 ToolCallingAdvisor 的内部历史关掉了、又没有配记忆 Advisor，工具回合里模型只收到系统提示词和工具结果，这才是项目当初认为“多厂商工具调用不兼容”的真正原因。在此基础上我设计了一个带工具预算和循环上限的追问决策 Agent……（后半句按你的实际工作填写）

    判定标准：什么算 Agent

    项目自带的面试参考（resources/skills/ai-agent-dev/ai-agent-dev.md）给了一句很好用的标准：“Agent 由 AI 决策下一步，工作流由预定义路径驱动。”把它细化成几个可以逐条核对的问题：

    问题工作流Agent
    下一步做什么由谁决定代码模型
    调哪个工具、调几次代码写死，或者根本没有工具模型在循环里决定
    什么时候结束代码的控制流走完模型不再请求工具，或触发步数、预算、超时上限
    出错怎么办代码里的重试与降级模型看到错误后自行调整，外加代码兜底
    结果可复现性高，路径固定低，路径随模型决策变化

    业界常用的划分（Anthropic 在 Building effective agents 一文中的归纳）把工作流再细分为提示链、路由、并行化、编排者-执行者、评估者-优化者五种模式，Agent 则是模型在循环中自主使用工具、直到完成任务。下图把项目里的各个环节放到“决策权”的光谱上。

    一个容易被忽略的事实：意外的自主性

    第 1、2、5、6、7、8、12 这 7 个调用点用的是默认配方，每次请求都附带 Skill 工具的定义：工具描述约 2.2K 字符（cl100k 估算约 895 token），里面列出全部 10 个面试方向的名称和说明（实验 E2）。这些调用点的提示词都没有要求使用工具，但 SkillsTool 自带的工具描述写着“当用户让你完成任务时，先检查可用的技能能否帮上忙”。

    于是出现了一个结构性问题：这些步骤名义上是工作流，模型却随时可以自作主张调用工具；而默认配方恰好关掉了工具回合的对话历史，一旦模型调用工具，下一次请求里只剩系统提示词和工具结果，用户输入整个丢失（实验 E1）。工作流里不该有的自由，正是隐患的触发条件。

    对照经典模式

    模式项目里的实例为什么这样用可以怎么进一步
    提示链
    Prompt chaining    		RAG：改写 → 检索（代码）→ 生成 → 探测窗口（代码）；题库：探针检索 → 生成 → 清洗去重（代码）每一步的输入输出确定，步骤之间可以插入代码做“门控”（没检索到就不调模型）在改写之前加一步“这个问题需要检索吗”的判断
    路由
    Routing    		邀约解析规则优先、模型兜底；按问题长度选 topK 和阈值；三种 ChatClient 配方；按会话选 Provider便宜确定的路径先走，贵的兜底路由依据写死在代码里，可以换成“规则 + 小模型分类”的级联
    并行化 · 分段
    Sectioning    		简历深挖题与方向题按 6:4 并行生成，互为降级两路上下文独立，并行把等待时间减半—
    并行化 · 投票
    Voting    		没有—评估可对同一批次采样 3 次取中位数，降低评分方差，代价是成本 ×3
    编排者-执行者
    Orchestrator-workers    		没有动态编排；评估的“分批 + 汇总”是静态的 map-reduce，批次由代码按 8 题一批切任务结构固定，不需要模型做规划若按知识点动态拆分评估维度，可以让编排者先规划
    评估者-优化者
    Evaluator-optimizer    		结构化输出的修复型重试（评估者是 JSON Schema 校验器）；题库“草稿 → 人工审核 → 启用”（评估者是人）格式问题用机器校验最便宜，内容质量交给人题库生成后加一个 LLM 评审（重复题、元信息题、能否从资料中作答），人只复核评审没通过的
    自主 Agent 循环语音面试：模型决定是否调用 Skill，ToolCallingAdvisor 循环到模型不再请求工具为止开放式对话工具只用来加载人设，属于“为了用工具而用工具”，见 机制拆解 · Skills
    人在回路
    Human-in-the-loop    		题库草稿人工启用；语音识别结果可编辑、手动提交；JD 修改后必须重新解析把模型的不确定性交给用户确认—

    用项目自带的标准审计：Harness 六层

    项目自带的参考把 Agent 拆成“模型 + Harness（模型之外的一切）”，并说“模型决定上限，Harness 决定下限”。下表用它列出的六层逐一审视项目本身。评级是相对生产级 Agent 系统而言；缺口里的 A 编号对应 源码实验页的 Agent 专项发现。

    层这个项目做了什么缺口评级
    L1 信息边界
    系统提示词、约束、角色    		17 个 StringTemplate 模板，系统与用户提示词分离；用户数据用带随机 UUID 的边界标签包裹；Skill 人设按方向注入可信的人设被包进“数据边界”，与防注入指令冲突（A06）；评估人设对所有方向都是 Java 后端专家（A08）可用，有冲突
    L2 工具系统
    注册、Schema、权限    		只有一个只读工具 Skill（spring-ai-agent-utils 的 SkillsTool）工具定义附在所有默认配方请求上（A10）；没有工具级预算、超时和权限模型很薄
    L3 执行编排
    循环、分支、并行    		Redis Stream 持久化执行；状态机与 taskId 围栏；并行出题；分批评估；工具循环交给框架默认配方的工具回合丢失用户消息（A01）；工具循环没有步数上限（E6）工作流强，循环弱
    L4 记忆与状态
    短期、长期、持久化    		会话状态 Redis 与数据库双写；RAG 最近 10 条作为真实消息；语音“窗口 + 增量摘要”压缩；topicSummary 历史去重摘要模板变量不替换（A04）；记忆 Advisor 一开就报错（A09）；没有跨会话的学习者画像有雏形，两处开启即坏
    L5 评估与可观测
    质量评估、追踪、指标    		结构化输出调用指标；语音链路时延指标；业务上有 LLM 评委没有评估“评委”的金标集；没有 token 与成本统计；指标看不到真实的模型调用次数（A12）；没有链路追踪最弱
    L6 约束与恢复
    错误处理、重试、降级    		修复型重试、分级降级、幂等键、围栏令牌、恢复调度、事务外调用模型两层重试相乘，最坏 8 次模型请求（A03）；降级吞掉失败（简历 0 分报告）；关键词护栏误伤导致降级（A02）最强
    面试这样说

    如果只能补一层，我会补 L5。这个项目的 L6（重试、降级、幂等）做得很扎实，但 L5 几乎是空白：没有金标集去衡量出题和评估的质量，也看不到每次请求的 token 和真实的模型调用次数。没有 L5，L1 到 L4 的任何改动，改 Prompt、换模型、加工具，都只能凭感觉判断好坏。我的理解是，L6 决定系统的下限，L5 决定你能不能持续把上限往上推。

    强项与短板

    强项

    • 失败语义清晰的工作流：结构化输出、修复型重试、分级降级。
    • 持久化执行：Stream 至少一次投递、状态机、围栏令牌、恢复调度。
    • 处处有上下文预算：简历、参考题库、基线、历史题都有截断上限。
    • 分层的注入防御思路，且没有写工具，注入的最坏影响有限。
    • 实时语音的流水线并行：边生成边按句合成、有序下发。

    短板

    • 工具与循环层很薄，唯一的工具循环还有历史截断隐患。
    • 没有评测体系，Prompt 和模型的改动无法回归。
    • 可观测只到“耗时”，看不到 token、成本、工具调用和决策。
    • 护栏靠关键词，会误伤候选人的正常回答。
    • 记忆相关的两个开关（摘要压缩、记忆 Advisor）一开启就出错。

    为什么大多数环节不该用 Agent

    • 结果要被打分和复用：题目和评估报告会落库、会被比较，路径固定才能复现、回归和排查。
    • 时延预算：每多一次工具调用就多一次完整的模型往返。语音一轮对话本来就要串起识别、生成、合成三段；文字面试创建时已经有两路并行的模型调用。
    • 成本：Agent 的 token 随步数累积（每一步都要带上完整历史），而这些任务一步就能完成。
    • 失败可控：工作流的每一步都能单独重试和降级；Agent 失败时，很难判断卡在第几步、该重试哪一步。
    • 安全：没有写工具，注入成功的最坏结果是“一次输出被污染”，而不是“执行了危险动作”。这个项目真正的安全边界其实在这里，而不在关键词过滤。

    反过来，值得升级成 Agent 的是“下一步取决于上一步结果”的环节：面试中的追问决策（答得好就换题，答不好就追问遗漏的点）、跨资料的查证式问答、根据多次面试结果制定练习计划。设计方案见 Agent 化改造。

    面试时怎么定性

    推荐的说法

    • “一个以工作流为主、在语音面试里有一个工具调用循环的大模型应用。”
    • “我分析过它为什么大部分环节不用 Agent，也验证过它唯一的工具循环存在的问题。”
    • “如果升级成面试官 Agent，我会这样设计循环、工具、终止条件和评估……”

    避免的说法

    • “我做了一个 AI 面试 Agent。”被追问“Agent Loop 怎么终止、工具怎么设计”时就会露馅。
    • “用了 Tool Calling，所以是 Agent。”出题早在 d0e7c41 就不再用工具。
    • “多 Agent 协作。”项目里没有。
    一条底线

    定性要比项目“小”一点，分析要比项目“深”一点。面试官追问的深度取决于你自己给出的定性：说成工作流，他会问编排和可靠性，这正是项目最强的部分；说成自主 Agent，他会问规划、记忆、多步推理和评测，这正是项目最弱的部分。
